# PR-5 Windows 実機確認の手順（Chrome・Edge）

計画書（[ui-redesign-implementation-plan.md](ui-redesign-implementation-plan.md)）第8.5節の確認を、Windows のインストール済みの **Google Chrome と Microsoft Edge の両方**で行うための手順です。対象は PR-5 の作業ブランチ `claude/sharp-dijkstra-n526mz`（[PR #21](https://github.com/fujihara-masaki/fta-202605/pull/21)）の受入候補の SHA（報告と PR 本文に書いた SHA）です。

この手順書は確認の進め方をまとめたもので、受入の合否を決めるものではありません。合否、PR の作成と `feature/ui-redesign` へのマージは、利用者が判断します。

**確認の方式（2026-10-06 の利用者の方針を引き継ぐ）**：Windows の Chrome・Edge とも、可能な範囲を自動 E2E で確認し、自動化で確認できない変更箇所だけを実操作・目視で確認します。

- 自動 E2E：既存の `scripts/run_browser_e2e.ps1` を、Chrome は `-Channel chrome`、Edge は `-Channel msedge` で使います。同じテストをブラウザの指定だけ変えて実行します（PR-5 でスクリプトは変えていません）。
- 実操作・目視：PR-5 で変えた箇所のうち、自動化で確かめられない3点（第5節）だけです。PR-3・PR-4 の手動確認を繰り返すことはしません。表示倍率・ブラウザの拡大・狭い幅の確認は PR-7 です。
- **ブラウザの区別**：PR-4 では、Edge は通常の Edge Stable ではなく **Edge 152 Extended Stable** で確認し、利用者がそれを確認対象として受け入れました（2026-10-08）。今回も、実際に起動したブラウザの作成元・版・実行ファイル・チャンネルを記録し、Extended Stable を通常の Stable と書きません（`run-info.md` の「起動したブラウザ」の末尾に `extended` などのチャンネルが出ます）。どちらのチャンネルで確認するかは利用者が決めます。
- PR-4 の Windows 確認（`7a9d517`）は PR-4 の結果です。PR-5 の確認結果として流用しません。

| ブラウザ | 方式 | 対象の SHA | 状態 |
|---|---|---|---|
| Google Chrome | 準備確認 → 全必須 E2E（第3節）＋実操作・目視（第5節） | 受入候補：PR #21 のブランチの先頭（報告・PR 本文に書いた SHA。アプリとテストは `6cd414e` と同じ） | 未実施 |
| Microsoft Edge | 準備確認 → 全必須 E2E（第4節）＋実操作・目視（第5節） | 同上 | 未実施 |

## 0. 守ること

- 普段の DB、過去の確認用 DB、通常のブラウザのプロフィールは使いません。自動 E2E は記録フォルダの中の一時 DB・スタブ（AI: e2e-stub）・一時プロフィールで動きます。実操作・目視は、その回だけの新しい DB と AI: mock で行います（第5.1節）。
- Chrome と Edge は **同じ SHA** で確認します。順番に実行し（同時に実行しない）、ブラウザごとに新しい記録フォルダを作ります。
- 準備確認の成功や診断（`-Mode Diagnose`）の実施は、全必須 E2E の合格ではありません。一部のテストだけを実行した結果も、全必須 E2E の結果とは別に扱います。
- ブラウザが起動できない場合、同梱の Chromium に切り替えて合格扱いにすることはしません（スクリプトもしません）。その環境の未確認事項として、記録を渡してください。
- 試験を通す目的で、ブラウザの設定・企業のポリシー・プロキシ・Windows の表示倍率を変えないでください。テストの時間の上限やスキップ・除外の条件も変えません（favicon の 404 の既知の例外と PR3-LAYOUT の chrome-1905x945 の限定した許容は PR-3 の条件のまま。edge-1912x914 は一致が必要）。PR-5 でもこれらは変えていません。
- 記録にはローカルのパス（ユーザー名を含む）が入ります。外部へ上げる前に確認してください。

## 1. コードを取り出す

[manual-check-pr4.md](manual-check-pr4.md) 第1節と同じ方法で、確認する SHA を SHA ごとの別フォルダ（git worktree）に取り出します。

```powershell
cd C:\work\fta-202605                                   # 普段のリポジトリ（例）
git fetch origin claude/sharp-dijkstra-n526mz
git ls-remote origin refs/heads/claude/sharp-dijkstra-n526mz   # ブランチの先頭の SHA

git -C $wt status --short                               # 何も出ないこと

```

## 2. PowerShell の設定と自動確認専用の venv

新しい PowerShell を開くたびに、次を設定します（manual-check-pr4.md 第2節と同じ変数）。

```powershell
$sha  = "<確認する SHA（40桁）>"
$src  = "C:\fta-check\src-$($sha.Substring(0,7))\fta_tool"
$venv = "C:\fta-check\e2e-venv"            # PR-3・PR-4 で使った自動確認専用の venv（コードのフォルダの外）
$out  = "C:\fta-check\e2e"                 # 自動確認の記録フォルダを作る場所（コードのフォルダの外）
$ps1  = "$src\scripts\run_browser_e2e.ps1" # 確認する SHA と同じ版のスクリプト
```

- **venv の再利用**：PR-5 は `requirements.txt`・`requirements-dev.txt` を変えていません（Playwright 1.56.0、pytest-playwright 0.7.1 のまま）。PR-4 で使った venv をそのまま使います。版だけ確かめます。


  playwright 1.56.0・pytest-playwright 0.7.1 と出れば再利用できます。venv がない、または版が違う場合だけ、[manual-check-pr3.md](manual-check-pr3.md) 第12.3節の初回準備（`-Mode Setup`）を新しいフォルダで行います。既存の venv を上書きしないでください。

## 3. Google Chrome での自動確認

### 3.1 準備確認

```powershell
& $ps1 -Mode Preflight -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダ `<SHA7桁>-<日時>-chrome-preflight` ができます。判定「成功」、終了コード 0、「起動したブラウザ」が `Google LLC …` であること。
- 実行するのは PR-3・PR-4 と同じ7件（E-E01 の2件と PR3-LAYOUT の3寸法）です。**全必須 E2E の合格ではありません。**
- 失敗したら全件へ進まず、記録フォルダを渡してください。

### 3.2 全必須 E2E（準備確認が成功してから）

```powershell
& $ps1 -Mode Full -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダ `<SHA7桁>-<日時>-chrome-full` ができます。合格の条件：判定「合格」（`REQUIRED_IDS` のすべての受入項目が成功し、失敗・スキップ・未実施が0件）、終了コード 0。**件数そのものは条件にしません**（PR-4 の 258 件は PR-5 の期待件数ではありません）。
- `REQUIRED_IDS` は累積です。PR-5 で E-E14〜E-E18・PR5-LAYOUT が加わり（48 項目）、PR-1〜PR-4 の項目もすべて実行されます。
- 開発環境（Linux、headless）での所要時間は報告と計画書 第14.5節に書きます。Windows で画面を表示する実行は、それより長くかかる見込みです（PR-4 では Chrome 13分・Edge 15分程度）。実行中はテストのウィンドウを操作しないでください。

## 4. Microsoft Edge での自動確認（Chrome の後に）

Chrome の全必須 E2E が終わってから、同じ SHA・同じ venv で、`-Channel msedge` に替えて実行します。

```powershell
& $ps1 -Mode Preflight -Channel msedge -Venv $venv -OutRoot $out -ExpectedSha $sha
# 準備確認が成功したら
& $ps1 -Mode Full -Channel msedge -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダは `…-msedge-preflight`・`…-msedge-full` です。「起動したブラウザ」が `Microsoft Corporation …`（Edge の版とチャンネル）で、`run-info.md` の実行ファイルが `msedge.exe` であること。
- 合格・成功の条件は Chrome と同じです。

### 4.1 渡すもの（Chrome・Edge 共通）

ブラウザごと・実行ごとに、記録フォルダの `e2e-report.md` と `run-info.md`（失敗・中止のときは記録フォルダ全体）。**準備確認の記録も渡してください**（PR-4 では準備確認の原本を受け取っておらず、PowerShell の表示に基づいて記録しました）。

## 5. 実操作・目視（両ブラウザ、PR-5 の変更箇所だけ）

自動 E2E の後に、次の3点だけを、Chrome と Edge のそれぞれで行います（所要は各10〜15分の見込み）。

### 5.1 準備（ブラウザごとに新しい DB）

manual-check-pr4.md 第5.1節と同じ手順で、新しい DB・AI: mock のサーバーを 127.0.0.1:8001 で起動します（`$run` の末尾は `pr5-chrome`・`pr5-edge`）。

- 起動ログに `dotenv file not found`、`AI_PROVIDER                = mock`、`Uvicorn running on http://127.0.0.1:8001` が出ること。
- `http://127.0.0.1:8001/analyses/new` で分析を1つ作る（タイトル「PR5確認」、頂上事象「決済処理が停止した」）。
- 「② 一次要因」の「手動追加」で、一次要因「要因A」「要因B」を追加する（追加のたびに追加した要因が選ばれる）。「要因A」を選び、インスペクタの「手動追加」で二次要因「要因A1」を追加する。

### 5.2 実操作1：Microsoft IME での入力（インスペクタの編集欄・手動追加のダイアログ）

自動 E2E（E-E17）は、手動追加のダイアログの変換中の Enter を合成したキーイベント（`isComposing`）で確かめています。インスペクタの要因タイトル欄の Enter（保存）も同じ判定です。実際の Microsoft IME の変換確定の Enter は、ここで確かめます。

1. 「要因B」を選ぶ。インスペクタの「要因タイトル」の末尾に、IME で「かくにん」と入力して変換し、「確認」で **Enter で確定する**。
2. 確定の Enter で保存されないこと（「要因を保存しました」が出ない。保存状態は「入力中（未保存）」のまま）。
3. もう一度 Enter を押すと保存され、「保存済み」になり、構造ナビ・作業リストの名前も変わること。
4. 「② 一次要因」の「手動追加」を押し、ダイアログの要因タイトルに IME で「ついか」→「追加」と入力し、**Enter で確定する**。確定の Enter でダイアログが閉じない（追加されない）こと。もう一度 Enter を押すと追加され、ダイアログが閉じて追加した要因が選ばれること。
5. 説明・メモなどの複数行の欄では、IME の確定の Enter は変換の確定だけを行い、保存されないこと。変換を確定した後の通常の Enter は改行になり、保存されないこと（保存は「保存」ボタン）。

### 5.3 実操作2：インスペクタに未保存の入力がある状態での F5（ブラウザの標準の確認）

自動 E2E（E-E12 の既存の確認と、E-E15・E-E18 の画面内の確認）は、テスト用ブラウザでブラウザの確認が出ることを自動で応答して確かめています。実際のブラウザの確認の表示と取消は、ここで確かめます。

1. 「要因A」を選び、インスペクタの「メモ」に「（F5の確認）」と入力する（保存しない）。「入力中（未保存）」と出ること。
2. F5 を押す。ブラウザの標準の確認（文言はブラウザが決める）が出ること。画面内の3択のダイアログではないこと。
3. 「キャンセル」（このページに留まる）を選ぶ。メモの「（F5の確認）」が残り、「入力中（未保存）」のまま、選択も「要因A」のままであること。
4. もう一度 F5 を押し、今度は「再読み込み」を選ぶ。入力が消え、保存済みのメモ（空）に戻ること（下書きはブラウザに保存しない仕様）。

### 5.4 目視：新しい編集欄・ダイアログが読みやすく、隠れていないこと

自動 E2E（PR5-LAYOUT）は、1280×800 と利用者環境の実測値（1905×945・1912×914）で、下の要素が表示領域の中にあり、ほかの要素（通知を含む）に覆われず、文字が 12px 以上であることを確かめています。実際の画面での読みやすさは、ここで確かめます（最大化したウィンドウ、表示倍率・拡大は普段のまま。100% 以外の場合はその値を記録する）。

1. インスペクタの編集欄：「要因の内容」の7項目（要因タイトル・説明・メモ・直接要因評価・評価コメント・根拠・再発防止策の候補）、保存状態（保存済み／入力中（未保存））、下部の「取消」「保存」。インスペクタをスクロールしても「取消」「保存」が下端に見えていること。要因タイトルを空にして「保存」を押したときの理由（「保存できませんでした：要因タイトルは必須です」）。確認したら「取消」で元に戻す。
2. 要因の切替の確認：「要因A」のメモに入力したまま構造ナビで「要因B」を押し、3択のダイアログ（「編集を続ける」「破棄して移動」「保存して移動」と、変更の一覧・説明）を見る。「編集を続ける」で閉じ、選択とメモが残ること。最後に「取消」で入力を戻す。
3. 要因の削除：「要因A」を選び、「この要因を削除」を押す。ダイアログの対象名、子孫の件数と合計（「この要因の子孫 1件も一緒に削除されます（合計 2件）。」）、件数が画面を表示した時点の情報である旨、取り消せない旨。**「キャンセル」で閉じる**（削除しない）。
4. 手動追加：「② 一次要因」の「手動追加」を押し、追加先（「頂上事象の下の一次要因」）と2つの欄を見る。タイトルを空のまま「追加する」を押したときのダイアログ内の理由。「キャンセル」で閉じる。

それぞれ、文字が読め、ボタンが欠けたり重なったり、通知の下に隠れたりしていないことを確かめ、1〜4 の画面のコピーを保存します。読みにくい・隠れている場合は、その画面のコピーと見え方を記録してください。

### 5.5 後片付けと記録

manual-check-pr4.md 第5.5節と同じ手順でサーバーを止め、ポート 8001 が空いたことを確かめます。

記録フォルダの `results.md` に、ブラウザごとに次を書きます。

- 自動確認の記録フォルダの名前と判定（準備確認・全必須 E2E を分けて）。
- 実操作1〜2・目視の結果（OK／NG）と画面のコピーのファイル名。NG の場合は手順と見え方。
