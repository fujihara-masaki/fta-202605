# PR-6 Windows 実機確認の手順（Chrome・Edge）

計画書（[ui-redesign-implementation-plan.md](ui-redesign-implementation-plan.md)）第8.6節の確認を、Windows のインストール済みの **Google Chrome と Microsoft Edge の両方**で行うための手順です。対象は PR-6 の作業ブランチ `claude/pr6-generation` の受入候補の SHA（報告と PR 本文に書いた SHA）です。

この手順書は確認の進め方をまとめたもので、受入の合否を決めるものではありません。合否、PR の作成と `feature/ui-redesign` へのマージは、利用者が判断します。**開発環境での自動試験の成功は、Windows 実機での確認や PR-6 の受入の判断の代わりではありません。**

**確認の方式（2026-10-06 の利用者の方針を引き継ぐ）**：Windows の Chrome・Edge とも、まず準備確認 → 全必須 E2E を自動で行い、自動化で確認できない PR-6 の変更箇所だけを実操作・目視で確認します。

- 自動 E2E：既存の `scripts/run_browser_e2e.ps1` を、Chrome は `-Channel chrome`、Edge は `-Channel msedge` で使います（PR-6 でスクリプトは変えていません。ブラウザ別の試験基盤は作っていません）。
- 実操作・目視：第5節の項目だけです。生成中の遅延と一部の親の失敗は、既存の **E2E 用スタブサーバー**（`tests/e2e/stub_server.py`。実LLMを呼ばない）の設定ファイルで再現します。**サーバーの停止・再開は手順に含めません。**
- PR-5 の Windows 確認（`dbe1c04`）は PR-5 の結果です。PR-6 の確認結果として流用しません。PR-5 で記録がなかった事項（正式なチャンネルの区分、表示倍率・拡大率など）を、今回の記録で推測して補いません。

| ブラウザ | 方式 | 対象の SHA | 状態 |
|---|---|---|---|
| Google Chrome | 準備確認 → 全必須 E2E（第3節）＋実操作・目視（第5節） | 受入候補（報告に記載） | 未実施 |
| Microsoft Edge | 準備確認 → 全必須 E2E（第4節）＋実操作・目視（第5節） | 同上 | 未実施 |

## 0. 守ること

- 普段の DB、過去の確認用 DB、通常のブラウザのプロフィールは使いません。自動 E2E は記録フォルダの中の一時 DB・スタブ（AI: e2e-stub）・一時プロフィールで動きます。実操作・目視も、その回だけの新しいフォルダの DB と E2E 用スタブ（AI: e2e-stub）で行います（第5.1節）。
- Chrome と Edge は **同じ SHA** で確認します。順番に実行し（同時に実行しない）、ブラウザごと・実行ごとに新しい記録フォルダを作ります。
- 準備確認の成功や診断（`-Mode Diagnose`）の実施は、全必須 E2E の合格ではありません。一部のテストだけを実行した結果も、全必須 E2E の結果とは別に扱います。
- ブラウザが起動できない場合、同梱の Chromium に切り替えて合格扱いにすることはしません（スクリプトもしません）。その環境の未確認事項として、記録を渡してください。
- 試験を通す目的で、ブラウザの設定・企業のポリシー・プロキシ・Windows の表示倍率を変えないでください。テストの時間の上限、スキップ・除外の条件も変えません（favicon の 404 の既知の例外と PR3-LAYOUT の chrome-1905x945 の限定した許容は PR-3 の条件のまま。edge-1912x914 は一致が必要）。PR-6 でもこれらは変えていません。
- 記録にはローカルのパス（ユーザー名を含む）が入ります。外部へ上げる前に確認してください。

## 3. Google Chrome での自動確認

### 3.1 準備確認

```powershell
& $ps1 -Mode Preflight -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダ `<SHA7桁>-<日時>-chrome-preflight` ができます。判定「成功」、終了コード 0、「起動したブラウザ」が `Google LLC …` であること。
- 実行するのは PR-3〜PR-5 と同じ7件（E-E01 の2件と PR3-LAYOUT の3寸法）です。**全必須 E2E の合格ではありません。**
- 失敗したら全件へ進まず、記録フォルダを渡してください。

### 3.2 全必須 E2E（準備確認が成功してから）

```powershell
& $ps1 -Mode Full -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダ `<SHA7桁>-<日時>-chrome-full` ができます。合格の条件：判定「合格」（`REQUIRED_IDS` のすべての受入項目が成功し、失敗・スキップ・未実施が0件）、終了コード 0。**件数そのものは条件にしません**（PR-5 の 337 件は PR-6 の期待件数ではありません）。
- `REQUIRED_IDS` は累積です。PR-6 で E-G01〜E-G12 が加わり（60 項目）、PR-1〜PR-5 の項目もすべて実行されます。
- PR-6 の試験には、10秒を超える待機の表示を確かめるもの（E-G09、約11秒）や、反映が遅い間の制限を確かめるものがあります。
- `test_edit_generation_leave.py` の `_real_bfcache` の2件（E-G08・E-G12。PR #22 のレビュー R7）は、同じチャンネルのブラウザを**このテストのためだけにもう1つ起動**し、Playwright が付ける `--disable-back-forward-cache` を外して、実際に別のアドレスへ移動して「戻る」で戻ります。戻った画面が `pageshow.persisted === true` の同じ文書でない場合（ブラウザがバックフォワードキャッシュから戻さなかった場合）は「…復元されませんでした（…）。このブラウザでは実ブラウザの復元を確認できません（未検証）」で失敗します。その場合も、試験を通すためにブラウザの設定や企業のポリシーは変えず、記録フォルダを渡してください。開発環境（Linux、headless）での所要時間は報告と計画書 第14.6節に書きます。Windows で画面を表示する実行は、それより長くかかる見込みです。実行中はテストのウィンドウを操作しないでください。

## 4. Microsoft Edge での自動確認（Chrome の後に）

Chrome の全必須 E2E が終わってから、同じ SHA・同じ venv で、`-Channel msedge` に替えて実行します。

```powershell
& $ps1 -Mode Preflight -Channel msedge -Venv $venv -OutRoot $out -ExpectedSha $sha
# 準備確認が成功したら
& $ps1 -Mode Full -Channel msedge -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダは `…-msedge-preflight`・`…-msedge-full` です。「起動したブラウザ」が `Microsoft Corporation …` で、`run-info.md` の実行ファイルが `msedge.exe` であること。合格・成功の条件は Chrome と同じです。

### 4.1 渡すもの（Chrome・Edge 共通）

ブラウザごと・実行ごとに、記録フォルダの `e2e-report.md` と `run-info.md`（失敗・中止のときは記録フォルダ全体）。**準備確認の記録（`e2e-report.md`・`run-info.md`）も渡してください**（PR-4・PR-5 では準備確認の原本を受け取っておらず、PowerShell の表示に基づいて記録しました）。

### 4.2 記録するブラウザの事実

今回確認できた事実だけを書きます（推測で補わない）。

## 5. 実操作・目視（両ブラウザ、PR-6 の変更箇所だけ）

自動 E2E の後に、次を Chrome と Edge のそれぞれで行います（所要は各20〜30分の見込み）。

### 5.1 準備：E2E 用スタブサーバー（ブラウザごとに新しいフォルダ）

生成中の状態を目で見るために、AI の応答を遅らせ、一部の親だけ失敗させます。自動 E2E が使うスタブサーバーを、その回だけの新しいフォルダで起動します（実LLMは呼ばず、外部への通信は遮断して記録します。DB はそのフォルダの中です）。

```powershell
$py  = "$venv\Scripts\python.exe"
$run = "C:\fta-check\runs\{0}-{1}-pr6-chrome" -f $sha.Substring(0,7), (Get-Date -Format "yyyyMMdd-HHmm")   # Edge の回は末尾を pr6-edge に
Test-Path $run                                   # False であること
New-Item -ItemType Directory -Path "$run\work", "$run\logs", "$run\screenshots" | Out-Null
Test-Path "$src\.env"                            # False であること
# 設定ファイルは BOM なしの UTF-8 で書く。Windows PowerShell 5.1 の Set-Content -Encoding UTF8 は
# BOM を付け、スタブ（UTF-8 で読んで json.loads）が読めずに既定の create に戻るため使わない。
$noBom = New-Object System.Text.UTF8Encoding($false)
function Set-StubControl([string]$json) { [System.IO.File]::WriteAllText("$run\work\stub_control.json", $json, $noBom) }
function Show-StubControl {
  # スタブと同じ読み方（UTF-8 で読み、json.loads）で、mode・delay_seconds・by_parent を表示する
  & $py -c "import json,pathlib,sys; d=json.loads(pathlib.Path(sys.argv[1]).read_text(encoding='utf-8')); print('mode=%s delay_seconds=%s by_parent=%s' % (d.get('mode'), d.get('delay_seconds'), ascii(d.get('by_parent'))))" "$run\work\stub_control.json"
  [System.IO.File]::ReadAllBytes("$run\work\stub_control.json")[0..2] -join ' '   # 先頭3バイト
}
# 遅延 20 秒（親ごと）。「要因B」を親にした要求だけ失敗させる（部分失敗の通知の確認用）。
Set-StubControl '{"mode": "delay", "delay_seconds": 20, "by_parent": {"要因B": "error"}}'
Show-StubControl
$env:PYTHONPATH = $src
$env:FTA_E2E_WORKDIR = "$run\work"
$server = Start-Process -FilePath $py -PassThru -NoNewWindow `
  -ArgumentList @("-m", "tests.e2e.stub_server", "--port", "8001") `
  -WorkingDirectory "$run\work" `
  -RedirectStandardOutput "$run\logs\stdout.log" -RedirectStandardError "$run\logs\stderr.log"
Start-Sleep -Seconds 5
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8001/ | Select-Object StatusCode   # 200
```

- ブラウザを最大化し、`http://127.0.0.1:8001/analyses/new` で分析を1つ作る（タイトル「PR6確認」、頂上事象「決済処理が停止した」）。編集画面のヘッダーに「AI: e2e-stub」と出ること。
- 「② 一次要因」の「手動追加」で一次要因「要因A」「要因B」「要因C」を追加し、A と B を Yes にする（C は未評価のまま）。
- `Show-StubControl` の表示が `mode=delay delay_seconds=20 by_parent={'\u8981\u56e0B': 'error'}`（`\u8981\u56e0B` は「要因B」）で、先頭3バイトが `123 34 109`（`{"m`）であること。`239 187 191` で始まる場合は BOM 付きで、スタブは設定を読めずに既定の create で動くため、確認を始めずに書き直す。Python がエラー（`JSONDecodeError` など）を出した場合も同じ。
- 遅延と失敗の設定は `Set-StubControl` で書き換えると、次の要求から変わります（サーバーの再起動は不要）。書き換えた後も `Show-StubControl` で確かめる。例：遅延をやめる `Set-StubControl '{"mode": "create"}'; Show-StubControl`（`mode=create delay_seconds=None by_parent=None`）。
- この書き込みと確認の手順は、開発環境（Linux の Python）で同じ読み方の確認（BOM 付きでは `json.loads` が失敗し、BOM なしでは読めること）をしただけで、**Windows PowerShell 5.1・7 では実行していません**。実機での結果を記録してください。
- Edge の回では Chrome の回のフォルダ・DB を使いません（上の `$run` を新しく作る）。

### 5.2 実操作1：下書きがない状態での生成中の F5

自動 E2E（E-G08）は、テスト用ブラウザで標準の確認（beforeunload）が出ることを自動応答で確かめています。実際の表示と取消は、ここで確かめます。

1. 何も入力していない状態で、「③ 二次要因」の「Yesの一次要因から二次要因を生成」を押す。作業エリアの上に「生成中（二次要因の通常生成・1/2件目の親）：…」が出ること。
2. 生成中に F5 を押す。ブラウザの標準の確認（文言はブラウザが決める）が出ること。画面内のダイアログではないこと。
3. 「キャンセル」（このページに留まる）を選ぶ。生成の表示が続き、約20秒後に終わること（「要因B」の要求はスタブの設定ですぐ失敗します）。終了後、「要因A」の下に3件ができ、「要因B」は「処理失敗」になること（5.4 で読みやすさを見ます）。
4. 終了後にもう一度 F5 を押す。今度は確認が出ずに再読み込みされ、③の生成ログに「再読み込み前の結果です。件数は実行時点の値です…」が出ること。

### 5.3 実操作2：Microsoft IME（PR-6 で変えた入力欄）

PR-6 で変えた入力欄は、生成中のヘッダーのタイトル（保存しない扱い）と、取得待ち・取得済みのインスペクタの欄です。自動 E2E（E-G11）は Enter とフォーカスの移動を合成した操作で確かめています。

1. 「要因A」を選んで詳細が表示されてから、生成を始める（5.2 の 1）。生成中にヘッダーの ✎ で分析タイトルを開き、IME で「かくにん」→「確認」と入力して **Enter で確定する**。確定の Enter では何も起きない（エラーも出ない）こと。
2. もう一度 Enter を押す。「生成中のため保存していません（生成が終わると保存できます）」が出て、入力が残ること。
3. 生成中に「要因C」を選んでから「要因A」（生成の前に詳細を読み込んだ要因）に戻り、メモに IME で入力して確定する。取得時刻付きの「生成の前（hh:mm:ss）に読み込んだ保存済みの内容です」が出て、入力できること。「保存」は押せないこと。
4. 生成の終了後、タイトルの Enter で保存できること、メモの入力が残り「保存」で保存できること。

### 5.4 目視：PR-6 で加えた表示の読みやすさ

自動 E2E は表示の文と状態を確かめています（E-G02〜E-G04・E-G06・E-G09〜E-G12）。画面での読みやすさ・見落としにくさは、ここで確かめます（最大化したウィンドウ、表示倍率・拡大は普段のまま。100% 以外の場合はその値を記録する）。

1. **操作バー**（③）：通常生成・追加生成・手動追加の3つの区別、「対象：Yesの一次要因 2件：「要因A」「要因B」（絞り込みで表示していない要因も含みます）」、親1件あたりの件数（設定値）、頂上事象の扱いの文。
2. **生成中の状態表示**（作業エリアの上）：「生成中（…・n/N件目の親）」と、保存・評価・追加・削除・出力・移動ができない旨。押せないボタン（評価・手動追加・削除・生成・①の保存）と、押せないリンク（一覧へ・ヘッダーのメニュー・出力）が見分けられること。
3. **生成準備の待機**：生成中でない状態で、別のタブで同じ分析を開き、そちらで「Yesの一次要因から二次要因を生成」を押す（サーバーが20秒ふさがる）。元のタブで①の頂上事象を変えて「頂上事象を保存」を押し、すぐに「③」の生成を押す。「生成の準備中（…）：「頂上事象」の保存が終わるのを待っています。」と「生成を取りやめる」が出ること。10秒を過ぎると「サーバーが別の処理（生成など）を実行中の可能性があります…」が加わること。「生成を取りやめる」を押すと「生成を取りやめました。生成の要求は送っていません…」が出ること（頂上事象の保存は取り消されない）。※サーバーの停止は不要です。
4. **取得待ち**：生成中に、まだ選んでいない要因（例：生成で増えた要因ではなく「要因C」）を選ぶ。インスペクタの欄が空で編集できず、「詳細（説明・メモ・直接要因評価など）は生成の完了後に取得します（取得待ち）。」が出ること。前の要因の内容が残っていないこと。
5. **生成ログと部分失敗の通知**：終了時の警告「二次要因の通常生成：3件作成、1件の親で失敗しました（詳細は生成ログ）」、生成ログ（「この分析で YYYY-MM-DD HH:MM に実行した生成の結果」、親ごとの「作成 3件」「処理失敗」と理由、要約、保持範囲の説明、「閉じる」）、③の親の見出しのバッジ。色だけでなく文字で区別できること。
6. **再読み込み前の結果**（5.2 の 4 の後）：「再読み込み前の結果です…」の注記と、バッジの「前回：…」。「閉じる」で消えること。

それぞれ、文字が読め、ボタンが欠けたり重なったり、通知の下に隠れたりしていないことを確かめ、画面のコピーを保存します。読みにくい・隠れている場合は、その画面のコピーと見え方を記録してください。

### 5.5 実操作3：別のタブで開いたときのログ（開き方ごと）

自動 E2E（E-G06）は「アドレスを入力した新しいタブ相当（opener なし）」と「`window.open` で開いたタブ（保存領域が引き継がれる）」を確かめています。ブラウザの機能でのタブの開き方は、ここで確かめます。生成ログが出ているタブで、次の開き方ごとに、新しいタブの③に生成ログが**出るか出ないか**を記録します（期待：出ない。出た場合は、計画 第8.6節の受入条件6「別タブでは出ない」との**差異**として、開き方・ブラウザ・画面のコピーを記録する。修正するか、制約として採用するかは利用者が判断する。既知の制限として受け入れ済みとは記録しない）。

| 開き方 | 記録 |
|---|---|
| 新しいタブを開き、アドレス欄に同じ分析の URL を入力 | 出る／出ない |
| 構造ナビなどのリンクではなく、ヘッダーの「分析一覧」を Ctrl+クリック → 一覧から同じ分析を開く | 出る／出ない |
| タブを右クリック →「タブを複製」 | 出る／出ない（ブラウザが sessionStorage と window.name を複製すると出る可能性がある。開発環境では未確認） |

### 5.6 実操作4：生成中に別のアドレスへ移動して「戻る」（PR #22 のレビュー R7）

自動 E2E（E-G08・E-G12 の `_real_bfcache`）は、テスト用に起動した Chromium で、実際の移動と「戻る」の後の状態を確かめています（開発環境の Linux の headless の Chromium 141 だけで確認）。Windows の Chrome・Edge の通常のウィンドウでの動きを、ここで確かめます。

1. `Set-StubControl '{"mode": "delay", "delay_seconds": 20}'; Show-StubControl`（`mode=delay delay_seconds=20 by_parent=None`）で、どの親も20秒かかるようにする。要因A・要因B が Yes であること（5.1）。
2. 次で、スタブが受けた生成の要求の数を表示できるようにする：`function Show-StubCalls { if (Test-Path "$run\work\stub_calls.jsonl") { (Get-Content "$run\work\stub_calls.jsonl" | Measure-Object -Line).Lines } else { 0 } }`。`Show-StubCalls` の値を控える（N0）。
3. 「③ 二次要因」の生成を押し、「生成中（…・1/2件目の親）」が出たら、アドレス欄に `http://127.0.0.1:8001/` を入力して Enter。ブラウザの標準の確認で**移動する（このページを離れる）**を選ぶ。サーバーが「要因A」の要求を処理している間は、一覧の表示を待たされることがあります（最大20秒ほど。開発環境のスタブではそうなりました）。
4. 一覧が表示されてから約30秒待ち、`Show-StubCalls` の値（N1）を控える。ブラウザの「戻る」を押す。
5. 戻った画面で次を確かめ、画面のコピーを保存する。
   - 作業エリアの上の「生成中」「結果を反映しています」の表示がなく、評価・手動追加・生成のボタンが押せること（数秒以内）。
   - ③の生成ログに「生成中…」「待機中」がなく、親ごとに「作成 3件」・「結果不明」・「送信していません」のいずれかであること（復元された場合の説明は「ページを離れたため、この親の結果を確認できていません…」「ページを離れたため送信していません（戻った後も自動では送信しません）」。再読み込みになった場合は再読み込みの説明）。「通信失敗」がないこと。
   - 通知「ページを離れる前に実行中だった生成を終了しました。戻った後に生成の要求を送り直してはいません（サーバーでの処理は止めていません）。…」が出たか、出なかったかを記録する。**出た場合はバックフォワードキャッシュからの復元、出ずに生成ログに「再読み込み前の結果です」が出た場合は再読み込み**です（ブラウザが復元しないことがあり、どちらになるかはブラウザが決めます。どちらでも生成中の状態が残らないことが条件です）。
6. 約30秒待って `Show-StubCalls` の値（N2）を控える。**N2 が N1 と同じ**（戻った後に生成の要求が送られていない）こと。N1−N0 が 1 または 2 であること（同じ親に2回送っていない）。
7. もう一度生成を押し、通常どおり終わること。終わった後の F5 で確認が出ないこと。
8. 最後に `Set-StubControl '{"mode": "delay", "delay_seconds": 20, "by_parent": {"要因B": "error"}}'; Show-StubControl` で 5.1 の設定に戻す（他の確認の前に行った場合）。
