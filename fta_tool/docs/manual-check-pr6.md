# PR-6 Windows 実機確認の手順（Chrome・Edge）

計画書（[ui-redesign-implementation-plan.md](ui-redesign-implementation-plan.md)）第8.6節の確認を、Windows のインストール済みの **Google Chrome と Microsoft Edge の両方**で行うための手順です。対象は PR-6 の作業ブランチ `claude/pr6-generation` の受入候補の SHA（報告と PR 本文に書いた SHA）です。

この手順書は確認の進め方をまとめたもので、受入の合否を決めるものではありません。合否、PR の作成と `feature/ui-redesign` へのマージは、利用者が判断します。**開発環境での自動試験の成功は、Windows 実機での確認や PR-6 の受入の判断の代わりではありません。**

**確認の方式（2026-10-06 の利用者の方針を引き継ぐ）**：Windows の Chrome・Edge とも、まず準備確認 → 全必須 E2E を自動で行い、自動化で確認できない PR-6 の変更箇所だけを実操作・目視で確認します。

- 自動 E2E：既存の `scripts/run_browser_e2e.ps1` を、Chrome は `-Channel chrome`、Edge は `-Channel msedge` で使います（PR-6 でスクリプトは変えていません。ブラウザ別の試験基盤は作っていません）。
- 実操作・目視：第5節の項目だけです（2026-10-20 に利用者が承認した最小手順。自動 E2E で機能を確かめた項目は手で繰り返さない）。生成中の遅延は、既存の **E2E 用スタブサーバー**（`tests/e2e/stub_server.py`。実LLMを呼ばない）を環境変数で起動して再現します。**サーバーの停止・再開は手順に含めません。**
- PR-5 の Windows 確認（`dbe1c04`）は PR-5 の結果です。PR-6 の確認結果として流用しません。PR-5 で記録がなかった事項（正式なチャンネルの区分、表示倍率・拡大率など）を、今回の記録で推測して補いません。

## 0. 守ること

- 普段の DB、過去の確認用 DB、通常のブラウザのプロフィールは使いません。自動 E2E は記録フォルダの中の一時 DB・スタブ（AI: e2e-stub）・一時プロフィールで動きます。実操作・目視も、その回だけの新しいフォルダの DB と E2E 用スタブ（AI: e2e-stub）で行います（第5.1節）。
- Chrome と Edge は **同じ SHA** で確認します。順番に実行し（同時に実行しない）、ブラウザごと・実行ごとに新しい記録フォルダを作ります。
- 準備確認の成功や診断（`-Mode Diagnose`）の実施は、全必須 E2E の合格ではありません。一部のテストだけを実行した結果も、全必須 E2E の結果とは別に扱います。
- ブラウザが起動できない場合、同梱の Chromium に切り替えて合格扱いにすることはしません（スクリプトもしません）。その環境の未確認事項として、記録を渡してください。
- 試験を通す目的で、ブラウザの設定・企業のポリシー・プロキシ・Windows の表示倍率を変えないでください。テストの時間の上限、スキップ・除外の条件も変えません（favicon の 404 の既知の例外と PR3-LAYOUT の chrome-1905x945 の限定した許容は PR-3 の条件のまま。edge-1912x914 は一致が必要）。PR-6 でもこれらは変えていません。
- 記録にはローカルのパス（ユーザー名を含む）が入ります。外部へ上げる前に確認してください。

## 3. Google Chrome での自動確認

### 3.1 準備確認

```powershell
& $ps1 -Mode Preflight -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダ `<SHA7桁>-<日時>-chrome-preflight` ができます。判定「成功」、終了コード 0、「起動したブラウザ」が `Google LLC …` であること。
- 実行するのは PR-3〜PR-5 と同じ7件（E-E01 の2件と PR3-LAYOUT の3寸法）です。**全必須 E2E の合格ではありません。**
- 失敗したら全件へ進まず、記録フォルダを渡してください。

### 3.2 全必須 E2E（準備確認が成功してから）

```powershell
& $ps1 -Mode Full -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダ `<SHA7桁>-<日時>-chrome-full` ができます。合格の条件：判定「合格」（`REQUIRED_IDS` のすべての受入項目が成功し、失敗・スキップ・未実施が0件）、終了コード 0。**件数そのものは条件にしません**（PR-5 の 337 件は PR-6 の期待件数ではありません）。
- `REQUIRED_IDS` は累積です。PR-6 で E-G01〜E-G12 が加わり（60 項目）、PR-1〜PR-5 の項目もすべて実行されます。
- PR-6 の試験には、10秒を超える待機の表示を確かめるもの（E-G09、約11秒）や、反映が遅い間の制限を確かめるものがあります。
- `test_edit_generation_leave.py` の `_real_bfcache` の2件（E-G08・E-G12。PR #22 のレビュー R7）は、同じチャンネルのブラウザを**このテストのためだけにもう1つ起動**し、Playwright が付ける `--disable-back-forward-cache` を外して、実際に別のアドレスへ移動して「戻る」で戻ります。戻った画面が `pageshow.persisted === true` の同じ文書でない場合（ブラウザがバックフォワードキャッシュから戻さなかった場合）は「…復元されませんでした（…）。このブラウザでは実ブラウザの復元を確認できません（未検証）」で失敗します。その場合も、試験を通すためにブラウザの設定や企業のポリシーは変えず、記録フォルダを渡してください。開発環境（Linux、headless）での所要時間は報告と計画書 第14.6節に書きます。Windows で画面を表示する実行は、それより長くかかる見込みです。実行中はテストのウィンドウを操作しないでください。

## 4. Microsoft Edge での自動確認（Chrome の後に）

```powershell
# 準備確認が成功したら
& $ps1 -Mode Full -Channel msedge -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 記録フォルダは `…-msedge-preflight`・`…-msedge-full` です。「起動したブラウザ」が `Microsoft Corporation …` で、`run-info.md` の実行ファイルが `msedge.exe` であること。合格・成功の条件は Chrome と同じです。

## 5. 実操作・目視（最小手順。2026-10-20 に利用者が承認した再設計）

自動 E2E（第3節・第4節。Windows の実際の Chrome・Edge を headed で実行）で機能を確かめた項目は、手で繰り返しません。人が行うのは、自動 E2E では確かめられない次の4つだけです。各項目と自動 E2E の対応は第6節、残るリスクは計画書 第14.6節「手動確認の再設計」。

| 残した確認 | Chrome | Edge | 自動で確かめられない理由 |
|---|---|---|---|
| 5.3 Microsoft IME の変換の確定の Enter（生成中のタイトル・取得済みの欄） | 実操作 | 実操作 | 自動 E2E は合成のイベント（`isComposing`・keyCode 229）で、OS の IME を通らない |
| 5.2 生成中の F5 で出るブラウザ標準の確認 | 実操作 | 実操作 | 自動 E2E はダイアログを横取りして応答するため、画面に出る確認そのものを見ていない |
| 5.5 タブの複製での生成ログの表示の有無 | 実操作 | 実操作 | ブラウザの機能で、自動 E2E の対象外（`sessionStorage`・`window.name` を複製するかはブラウザが決める） |
| 5.4 代表画面の読みやすさ | 基準として目視 | Chrome との差異を中心に目視（文字の重なり・欠け・押せない箇所・通知による隠れがないことは必ず見る。省略ではない） | 読みやすさ・見分けやすさは人の判断 |

自動 E2E で代替し、手で再現しないもの：生成準備中の保存待ち（旧 5.4 の3：E-G09・E-E20）、詳細の取得待ちの機能（旧 5.4 の4：E-G10）、再読み込み後のログの機能（旧 5.4 の6：E-G06）、生成中に離れて戻る（旧 5.6：E-G08・E-G12 の実ブラウザの試験。Windows の Chrome・Edge で成功）、通常の新しいタブ・Ctrl+クリックで開いたタブ（E-G06）。部分失敗の生成ログの表示は、第5.6節の条件を満たす既存の画像で確かめ、ない場合だけ付録 A で再現します。

所要の見込み：準備 約5分、Chrome 約10分、Edge 約8分（既存の結果を流用できる項目はその分短くなる）。

### 5.1 準備：E2E 用スタブサーバー（ブラウザごとに新しいフォルダ、20秒の遅延）

第2節の変数（`$sha`・`$src`・`$venv`）を設定した PowerShell（Windows PowerShell 5.1 でよい）で、ブラウザごとに次を行います。普段の DB・過去の確認用 DB は使いません（DB は新しいフォルダの中にできます）。実LLMは呼ばず、外部への通信は遮断して記録します。

```powershell
$browser = "chrome"                              # Edge の回は "msedge"
$py  = "$venv\Scripts\python.exe"
$run = "C:\fta-check\runs\{0}-{1}-pr6-manual-{2}" -f $sha.Substring(0,7), (Get-Date -Format "yyyyMMdd-HHmm"), $browser
Test-Path $run                                   # False であること（True なら少し待って $run を作り直す）
Test-Path "$src\.env"                            # False であること
Get-NetTCPConnection -LocalPort 8001 -State Listen -ErrorAction SilentlyContinue   # 何も出ないこと（8001 番が空いている）
New-Item -ItemType Directory -Path "$run\work", "$run\logs", "$run\screenshots" | Out-Null
# スタブの設定は環境変数で渡す（設定ファイル stub_control.json は作らない）
$env:PYTHONPATH = $src
$env:FTA_E2E_WORKDIR = "$run\work"
$env:FTA_E2E_STUB_MODE = "delay"
$env:FTA_E2E_STUB_DELAY_SECONDS = "20"
$env:FTA_E2E_ACCESS_LOG = "$run\logs\access.jsonl"   # 要求ごとの受信・応答の時刻（遅延の確認に使う）
$server = Start-Process -FilePath $py -PassThru -NoNewWindow `
  -ArgumentList @("-m", "tests.e2e.stub_server", "--port", "8001") `
  -WorkingDirectory "$run\work" `
  -RedirectStandardOutput "$run\logs\stdout.log" -RedirectStandardError "$run\logs\stderr.log"
Start-Sleep -Seconds 5
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8001/).StatusCode   # 200 であること
Test-Path "$run\work\stub_control.json"          # False であること（設定ファイルを使っていない）
```

画面の準備（ブラウザを最大化。表示倍率・拡大は普段のまま。100% 以外ならその値を記録する）：

1. `http://127.0.0.1:8001/analyses/new` で分析を作る（タイトル「PR6確認」、頂上事象「決済処理が停止した」）。編集画面のヘッダーに「AI: e2e-stub」と出ること。
2. 「② 一次要因」の「手動追加」で「要因A」「要因B」「要因C」を追加し、A と B を Yes にする（C は未評価）。「要因A」を選び、詳細（説明・メモ）が表示されるのを待つ。

**遅延の確認**（スタブが環境変数を読み、実際に20秒待つこと）：次の第5.2節の最初の生成が終わった後に、次を実行します。

```powershell
Get-Content "$run\logs\access.jsonl" -Encoding UTF8 | ConvertFrom-Json |
  Where-Object { $_.path -like "*/generate/level/*" -and $_.event -eq "response_end" } |
  Select-Object path, ms                          # 親ごとの行の ms が 20000 以上であること
Get-Content "$run\work\stub_calls.jsonl" -Encoding UTF8 | Select-Object -Last 1   # "mode": "delay" を含むこと
```

- ms が 20000 未満、または `"mode": "create"` の場合は、環境変数が渡っていません。第5.7節の後片付けをしてから、第5.1節をやり直してください（確認は始めない）。
- この手順（環境変数の受け渡し、`ConvertFrom-Json` での集計）は、**Windows PowerShell では未実行**です（開発環境の Linux で、同じ環境変数（遅延だけ3秒にした）でスタブを起動し、生成の要求の ms が 3055.2、`stub_calls.jsonl` の最後の行が `"mode": "delay"`、設定ファイルがないことを確かめただけ）。結果を記録してください。

### 5.2 生成中の F5（ブラウザ標準の確認）と生成中の表示（Chrome・Edge）

自動 E2E（E-G08）は、生成中だけ確認が出ること、取り消すと生成が続くこと、終了後は出ないことを、テスト用の自動応答で確かめています。ここでは、ブラウザが実際に出す確認を見ます。

1. 「③ 二次要因」の「Yesの一次要因から二次要因を生成」を押す。作業エリアの上に「生成中（二次要因の通常生成・1/2件目の親）：…」が出る（親2件で約40秒）。
2. **目視（5.4 の2）**：この状態表示と、押せないボタン（評価・手動追加・削除・生成・①の保存）・押せないリンク（一覧へ・ヘッダーのメニュー・出力）が見分けられること。画面のコピーを `$run\screenshots` に保存する。
3. 生成中に F5 を押す。**画面内のダイアログではなく、ブラウザ標準の確認**（文言はブラウザが決める）が出ること。画面のコピーを保存する。
4. 「キャンセル」（このページに留まる）を選ぶ。生成の表示が続き、終わること。
5. 終わったら第5.1節の「遅延の確認」を行う。
6. **目視（5.4 の5・6）**：生成ログ（親ごとの「作成 3件」、要約、保持範囲の説明、「閉じる」）と、③の親の見出しのバッジ。もう一度 F5 を押す（確認は出ない）と、「再読み込み前の結果です…」の注記とバッジの「前回：…」が出ること。それぞれ画面のコピーを保存する。

### 5.3 Microsoft IME（Chrome・Edge）

自動 E2E（E-G11、E-E11）は Enter とフォーカスの移動を合成した操作で確かめています。ここでは OS の IME を通します。

1. 「要因A」を選んで詳細が出ている状態で、③の生成を押す（もう一度押してよい。生成のたびに要因が増えるのは問題ない）。
2. 生成中にヘッダーの ✎ で分析タイトルを開き、IME で「かくにん」→「確認」と変換して **Enter で確定する**。確定の Enter では何も起きない（エラーも出ない）こと。
3. もう一度 Enter を押す。「生成中のため保存していません（生成が終わると保存できます）」が出て、入力が残ること。

### 8.1 時計の分解能の確認（E-L01・E-L07 の原因の裏付け。1分）

E-L01・E-L07 について、開発環境では、分析の更新日時を同じ値にした限定再現で、Windows と同じ失敗になることを確かめました。一方、過去の Windows の実行で保存された更新日時の値は記録がなく、未確認です（同じ値だったことは、テストの操作の順からの推定です）。PR-6 では一覧の並び順の仕様（更新日時の降順）は変えず、テストで更新日時を明示しました（2026-10-14 の方針）。Windows の Python 3.12 で日時の刻みが粗いかを、自動確認専用の venv で確かめます（読むだけで、何も変えません）。

