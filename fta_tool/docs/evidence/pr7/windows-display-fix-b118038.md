## A：表示倍率 125%・拡大 125% のレイアウトの NG

### 根拠

- Windows の記録：ウィンドウ 1536×816（表示倍率 125% の論理画素）、拡大 100% の表示領域 1528×732、devicePixelRatio 1.25 → 表示領域の物理画素は 1910×915（拡大 100% の画面の大きさ 1910×915 と一致）。
- 拡大 125% では devicePixelRatio 1.5625。表示領域は 1910 ÷ 1.5625 = **1222.4**、915 ÷ 1.5625 = **585.6** CSS px。`clientWidth`×`clientHeight` はこれを整数にした 1222×585（切り捨て）。
- ペインの下端は 164.56 + 421.03 = 585.59。Chromium は位置を 1/64 CSS px 単位で決めるため、585.6 は 585.59375 になる。**ペインは表示領域の下端で終わっていて、はみ出していない**。物理画素では 585.59 × 1.5625 = 914.98 で、915 画素の中に収まる。
- 編集画面の高さは CSS で表示領域に合わせている（`height: 100vh` からヘッダーを引いた高さ。グリッドの行 `minmax(0, 1fr)`）。ペインが表示領域の下端に接するのは仕様どおり。
- 開発環境で同じ表示領域を2つの方法で再現した。
  - 表示倍率 1.5625（`--force-device-scale-factor=1.5625`、ウィンドウ 1220×670）：表示領域 1222.4×585.6、client 1222×585。
  - 実際のブラウザの拡大：表示倍率 1.25 に、一時プロフィールの既定の拡大 125%（`--zoom-in-profile`）。表示領域 1224.32×585.6、client 1224×585。
  - どちらも Windows の記録とペインの位置・大きさが同じになった（`center [0, 164.56, 882.4, 421.03]`）。表示倍率 1.5625 の再現で修正前の試験を実行すると、Windows と同じ NG（同じ値）になった（実際の拡大の再現は、修正後の試験だけで実行した）。
- 同じ表示倍率・拡大で、保存・取消の位置は Windows の記録（生成の結果の通知・エラーの通知のときの `[1161.1, 547.6, 45.3, 30]`）と開発環境の再現が同じ。保存・取消は表示領域の下端から 8px 上（577.6）で終わる。

### 仕様との整合（受入条件は変えていない）

- 受入条件（計画 第8.7節の条件1・2：ペインが表示領域の中にあり、保存・取消とダイアログのボタンがスクロールなしで見える）は変えていない。変えたのは、試験が使う**表示領域の測り方**だけ。
- 試験は、ページが実際に配置される表示領域（`visualViewport` の幅・高さ。ピンチの拡大がないとき。スクロールバーを除く）を使う。`clientWidth`×`clientHeight` は記録に残すが、境界には使わない。整数の値は、切り捨てになる場合（今回の Windows の 585.6 → 585）も、切り上げになる場合（2026-10-06 の 1905.6 → 1906、計画 第14.3節）もあり、表示領域の端を表さない。
- ペインの検査（`expect_layout`）の許容は、**実際の端から 1/64 px**（Chromium の配置の単位）にした。以前の「整数 + 0.5px」より厳しい。たとえば表示領域が整数（585）で、ペインが 585.3 まで出ている場合、以前は通り、いまは失敗する（単体試験で確認）。
- 操作の検査（`reach()`・`focus_shown()`・ダイアログの収まり）の許容は、以前と同じ 0.5px（操作の箱の端数のため）で、基準を実際の表示領域にした。表示領域が整数のときは以前と同じ。端数があるときは、基準が整数の値より最大 1px 未満ずれる（切り捨てなら外側へ、切り上げなら内側へ）。実際の端に対する許容は、整数の表示領域のときと同じ 0.5px。
- この変更は検証の方法の変更として、計画書 第14.8節に記録した。**2026-10-31 に利用者が承認した**（端数を含む実際の表示領域を基準にし、ペインの許容を 1/64 px に厳しくする）。**Windows での再確認（手順書 第3.0節の手順3）が合格することを受入条件とする。**

### 保存・取消などの操作性への影響

- Windows の表示倍率 125%・拡大 125% では、レイアウトの検査で NG になったため、その後の「入力の前と入力中の保存・取消」「主要な操作への到達」は Windows では**行われていない**（記録に残っているのは、生成の結果の通知・エラーの通知のときの保存・取消だけで、どちらも「表示のまま（スクロールなし・覆われない）」）。
- 開発環境の再現（1222.4×585.6、修正後の試験）では、7 項目すべて OK。保存・取消は、入力の前・入力中・生成の結果の通知・エラーの通知のどれでも「表示のまま」（`[1161.1, 547.6, 45.3, 30]`）。未保存確認・削除確認・手動追加のダイアログのボタン、保存失敗の表示、通知の表示中の Tab・Shift+Tab（30 回）も OK。
- **Windows での確認は未実施**です（下の「Windows での再確認」）。

## B：参考の条件の NG（計画の想定を下回る）

計画 第5.9.4節の想定は幅 1024px・高さ 500px で、それを下回る表示領域は「参考（判定に含めない）」として結果を残し、影響を示して利用者の判断を受ける。B の3つは、どれも高さ 500px 未満（488・470・392）で、計画の対象の範囲の外。**Windows の記録の NG は消さず、そのまま残す**（windows-2026-10-30-b35504f-display.md）。

### B-1・B-2（1018×488・1017×470）：レイアウトの NG

- 表示領域の幅は 1018.67（1528 × 1.25 ÷ 1.875）と 1017.6（1272 × 1.5 ÷ 1.875）CSS px で、ペインの右端はそこで終わっている。A と同じ試験の誤検知。
- 修正後の試験を、開発環境の実際の拡大（表示倍率 1.5 × 拡大 125%：表示領域 1017.6×469.87、表示倍率 1.25 × 拡大 150%：1020.27×488）で実行すると、7 項目すべて OK。保存・取消も「表示のまま」。
- 利用者への影響：レイアウトのはみ出しはない。高さが低いため作業エリアは狭い（1017.6×469.9 で、上の帯の下に約 211px）。
- 改善の要否：A の試験の修正以外は不要と考える（利用者の判断）。

### B-3（848×392）：通知が作業エリアのフォーカスと生成中の状態表示を覆う

**原因（開発環境で測定。表示倍率 1.5 × 拡大 150%：表示領域 848×391.56）**

- 構造ナビを折りたたんだ編集画面の作業エリアは、グリッドの1行目（`minmax(0, 1fr)`）。通知はその下の2行目（`auto`、上限は高さの 25% = 98px）。
- 幅 848px では、作業エリアの上の帯（タブと絞り込み）が2行に折り返して 123.3px。帯は縮まない。その下の作業エリアのスクロール領域には、上下の余白 16px + 32px（48px）がある。
- 通知がないとき、1行目は 226px（帯 123px + スクロール領域 103px）。
- 通知が1件出ると、1行目は 155.3px になる。帯と余白の合計 171.3px より低いため、スクロール領域が 16px 通知の行にはみ出し、作業エリアの一覧（とフォーカスのある項目）、生成中の状態表示の上に通知が描かれる。通知が上限（98px）まで出ると、はみ出しは約 43px。
- 計画の範囲では起きない見込み：高さ 500px で通知が上限（125px）まで出ても1行目は約 210px あり、幅 1017.6px のときの帯と余白（94.6px + 48px = 142.6px）より高い（幅 1024px 以上では帯は折り返しが少なく、低くなる）。幅 850px 前後では、高さが約 450px 未満で、通知が多いと起きる。

**利用者への影響**

- 対象：1280×720 の論理画面（例：1920×1080 の画面で表示倍率 150%）で、ブラウザの拡大を 150% にしたとき。
- 通知が出ている間（成功・お知らせは 3 秒、注意は 6 秒、エラーは閉じるまで）、作業エリアの下の方の項目と生成中の状態表示が通知に隠れる。Tab で移ったフォーカスが通知の下に入ることがある。
- 保存・取消（入力の前・入力中）と、ダイアログのボタンは隠れない（Windows の記録でも「表示のまま」）。
- 回避：通知の「閉じる」（Tab で届く）、時間がたって消えるのを待つ、ブラウザの拡大を 125% 以下にする（Ctrl と -）。

**改善の候補（今回は実装していない）**

| 案 | 内容 | 影響 |
|---|---|---|
| 1. このまま | 計画の想定外として、拡大を下げる運用にする | 変更なし |
| 2. 低い高さで上の帯もスクロールさせる | 作業エリアの1行目が帯と余白より低いときは、帯を含めて作業エリア全体をスクロールさせる | 低い高さでは、タブ・絞り込みが一覧と一緒に隠れる |
| 3. 通知の上限を作業エリアに合わせる | 通知の行の上限を、作業エリアの最小の高さ（帯と余白）を残す値にする | 低い高さでは通知が1件分ほどしか見えず、通知の中のスクロールが増える |
| 4. 帯を1行にする | 幅 1024px 未満で、絞り込みを折り返さない（縮める） | 絞り込みの入力欄が狭くなる |

どの案も、計画の範囲（高さ 500px 以上）の表示は変えないように作れる見込みだが、試していない。

## 画面（screens）が左上の一部だけ

- Windows の拡大 125%・150% の画面は 1528×731・1273×610（表示倍率 125%）と 1526×705・1272×588（150%）で、表示領域の物理画素（1910×915・1908×882）の左上の一部だった。インスペクタの右側と保存・取消の帯が写っていない。
- 原因：Playwright の `page.screenshot` は、表示領域の CSS の大きさを拡大前の大きさとして切り取る。開発環境で、実際の拡大 125%（表示倍率 1.25）で同じことを確かめた（`page.screenshot` は 1530×708、表示領域は 1913×885）。
- 修正：道具の `save_window()` が、Chromium の `Page.captureScreenshot`（切り取りなし）で表示領域の全体を物理画素で保存する。失敗したときだけ `page.screenshot` に戻り、その方法と理由を `result.md` に書く。`result.md` には各画面の大きさも書く。
- 確認（開発環境）：実際の拡大 100・125・150%（表示倍率 1.25、表示領域の物理画素 1913×915）で、全部の画面が 1913×915 になった。
