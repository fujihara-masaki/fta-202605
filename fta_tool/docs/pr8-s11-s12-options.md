## 1. 前提：どのようなデータで起きるか

S-11・S-12 は、**親子関係に不整合がある要因**（別の分析の要因を親にしている、自己参照、循環など。計画 第5.9.5節の区分）があるときだけ起きる。

- 画面と既存の API の通常の操作では、こうしたデータは作られない：手動追加（`POST /nodes/{id}/children`）は子を親と同じ分析に作り、生成は同じ分析の要因だけを親にする（`node_map` が分析内の要因だけ）。
- 起こりうる経路（いずれも未確認）：DB の直接編集、過去の版の不具合、計画 第2.4節の M-2〜M-4（並行処理の構成で、生成中に親が削除されると親のない子ができ、SQLite が削除された ID を再利用すると、その子が別の分析の要因を親として指す）。利用者の DB にこうしたデータがあるかは**未確認**（計画 第12.2節）。
- 編集画面は不整合を区分して表示し、安全性を確かめられない削除・生成をしない（PR-3、判断2・判断3）。**これは画面が取得した時点の情報による画面側の抑止で、API の安全性の保証ではない。**

## 2. 現在のコードで未解決の範囲（2026-11-02、`254f826`）

### S-11 分析をまたぐ連鎖削除と、不正な親子関係の安全な削除・修復

| 経路 | 現在の動作 | 画面の抑止 |
|---|---|---|
| **一覧からの分析全体の削除**（`POST /analyses/{id}/delete`。`main.py` の `delete_analysis` → `crud.delete_analysis`） | 分析の要因を ORM の連鎖削除（`models.py` の `Analysis.nodes` と `Node.children`、`cascade="all, delete-orphan"`）で消す。`Node.children` は分析を区別しないため、**親がこの分析の要因である別の分析の要因も削除される**（HTTP 200）。自己参照・循環の要因があると HTTP 500 で、何も消えない | **なし**。一覧の削除ダイアログ（`list.js` の `openDeleteDialog`）は件数（`crud.count_nodes_by_analysis`。この分析の要因だけ）を示すだけで、別の分析の子孫を調べない。**利用者の画面操作だけで起きる経路** |
| 編集画面の要因の削除（`POST /nodes/{id}/delete`。`crud.delete_node`） | 同じ連鎖削除で、`parent_id` でたどれる別の分析の子孫も削除する。自己参照・循環では HTTP 500 で何も消えない | あり（PR-3 判断2）：サーバーが削除範囲を走査し（`detail_view.deletion_scope`）、別の分析の要因を含む・走査を完了できない・確認用の問い合わせに失敗した場合はボタンを無効にし、ダイアログを開く時と確定の直前にも判定する。**画面の取得の後の変化（別のタブなど）と API の直接呼び出しには効かない** |
| 不正な要因の修復（親の付け替え、自己参照・循環の解消） | 画面にも API にも手段がない | 自己参照・循環・別分析への親参照・階層不一致の要因は、編集画面から削除できない（判断2-4） |

### S-12 生成 API の循環の検出

| 経路 | 現在の動作 | 画面の抑止 |
|---|---|---|
| 親を指定した生成（`POST /analyses/{id}/generate/level/{n}`、`parent_id` あり） | 親の経路を作るループ（`main.py` の `generate_factors` の「Build parent path」、`while current is not None:`）に、たどった要因の記録も深さの上限もない。**親が循環上にあるか循環の下にあると、ループが終わらない**。**実測**（下の実行確認）：テスト用のクライアントで、要求が 20 秒以内に応答しなかった。**コードからの判断**（実測していない）：このループは `async def` の中の同期処理のため、そのプロセスのイベントループを止め、同じプロセスのほかの要求にも応答しなくなる。uvicorn を1プロセス（単一ワーカー。`--workers` を付けない既定の起動、README の起動方法）で動かしている場合は、**アプリ全体が応答しなくなる**。複数ワーカーでは、そのワーカーだけが止まり続ける | あり（PR-3 判断3）：不整合のある要因と「上位に不整合あり」の要因を親にしない。ボタンの無効化に加え、要求の送信の直前にも判定する（`generation.js`・`permissions.js`） |
| 親を指定しない二次・三次の生成（`parent_id` なし） | その階層の Yes の要因を**不整合の有無にかかわらず**すべて親にする。循環上の Yes の要因があれば、上と同じくループが終わらない | あり：画面は二次・三次で必ず `parent_id` を指定し、親指定なしの要求を送らない（判断3） |
| 親の階層の検査 | `parent_id` の要因の階層が「生成する階層 − 1」かを確かめない（S-9 の一部） | あり：画面は階層の合わない親を送らない |

**画面側の抑止（判断3）と API 側の循環の検出（S-12）は別のもの**である。前者は、この画面がそのような要求を送らないことを保証するだけで、API の直接呼び出し・別の画面・取得の後のデータの変化からの要求には効かない。

### 実行確認（2026-11-02、`254f826` のクリーンな worktree、一時ディレクトリの一時 DB）

アプリは変えず、テスト用のクライアント（`fastapi.testclient`）で既存の API を呼び、不整合は一時 DB に直接書き込んで作った。AI プロバイダは mock（実LLMなし）。各回は新しい一時ディレクトリ、メモリの上限 3GB、20 秒の時間制限。

| 確認 | 手順 | 結果 |
|---|---|---|
| S-11 一覧からの分析の削除 | 分析 X（一次1件）、分析 Y（一次2件、二次1件）。Y の二次の親を X の一次に書き換え、X を削除 | HTTP 200。X の要因 1 → 0、**Y の要因 3 → 2**（Y の二次が消え、Y の無関係な一次は残った） |
| S-11 要因の削除 | 同じデータで X の一次を `POST /nodes/{id}/delete` | HTTP 200。**Y の要因 2 → 1**（Y の二次が消えた） |
| S-11 循環を含む分析の削除 | 一次 A・二次 B で A の親を B に書き換え（A⇄B）、分析を削除 | HTTP 500。要因 2 件と分析は残った（何も消えない） |

制約として明記する内容（案2を選ぶ場合。PR-8 の文書には、案の判断が未決のため「未解決」として記載済み）：

1. 一覧からの分析の削除は、親がその分析の要因である**別の分析の要因も削除する**。削除の確認ダイアログの件数には入らない。不整合データがなければ起きない。

## 4. 比較の要点と判断事項

| 観点 | 案1（統合前に最小限の対策） | 案2（制約を明記して後続） |
|---|---|---|
| 利用者の画面操作だけで起きる被害（一覧からの分析の削除で別の分析の要因が消える） | 防ぐ | 残る（不整合データがある場合） |
| 終わらない生成の要求と、同じプロセスの停止（単一ワーカーではアプリ全体。S-12） | 防ぐ | 残る（API の直接呼び出しなど、画面以外の要求の場合） |
| 統合までの作業 | 別の PR の実装・試験・レビュー、受入候補の SHA の更新、Windows での再確認の要否の判断 | 文書だけ（PR-8 で完了） |
| 既存の受入の証跡の使い方 | PR-7 の Windows の記録（`b118038`）は新しい SHA の結果ではなくなる | そのまま根拠にできる（コードが同じ） |
| API 契約 | 異常時の応答が変わる（409 など）。利用者の承認が必要 | 変わらない |

利用者に判断を求めた点（2026-11-02 に判断済み。結果は第6節）：

1. **S-11**：案1（統合前に別の PR で対策）／案2（制約として明記し後続）のどちらにするか。案1の場合、拒否の応答（409 と理由の文）でよいか。分析の削除と要因の削除の両方を対象にするか。
2. **S-12**：案1／案2のどちらにするか。案1の場合、親を指定しない要求で不整合のある親を除くこと（対象の範囲の変更）を含めるか。
3. 案1を選ぶ場合：S-11 と S-12 を1つの PR にするか。新しい受入候補での Windows の確認（Chrome・Edge の Full の再実行など）を行うか、開発環境の試験だけで受け入れるか。
4. 案2を選ぶ場合：後続の対応の時期と、統合の前に利用者の DB の写しで不整合の有無を確かめるか。

PR-8 では、どちらの案でも進められる作業（文書の更新、試験、受入の準備）を完了している。**S-11・S-12 のアプリの改修は PR-8 に含めていない。**

## 6. 利用者の判断（2026-11-02）と実施の方針

**S-11・S-12 とも案1 を採用**した。PR #27（PR-8 の文書）とは別の **1つの専用 PR** にまとめ、S-11 と S-12 の変更・試験はコミットと試験の名前で別々に追えるようにする。**実装・試験・受入は未実施**（PR #27 のマージの後に着手する）。

### S-11（分析をまたぐ連鎖削除・不正な親子関係の削除）

1. **対象**：分析全体の削除（`POST /analyses/{id}/delete`。一覧の削除）と、要因の削除 API（`POST /nodes/{id}/delete`）の両方。
2. **削除の直前に、サーバー側で削除される範囲を検査する**（要因の削除はその要因と子孫、分析の削除はその分析の全要因と子孫。深さの上限なし、たどった要因を記録）。
3. 範囲に**別の分析の子孫**がある、**自己参照・循環**がある、**走査を完了できない**場合は、**データを変更せずに拒否**する。
4. 拒否は **HTTP 409** と、利用者が理解できる**日本語の理由**を返す。
5. **正常な削除と、対象不存在（404）などの既存の挙動は維持**する。
6. **実際の API の拒否の理由が既存の画面（一覧の削除ダイアログ、編集画面の削除ダイアログ）に表示されること**を E2E で確かめる。
7. 従来の巻き込み削除や 500 を期待している既存の試験は、**拒否とデータの不変**を確かめる試験へ更新する（2026-11-02 に確認した該当：`tests/test_node_integrity.py` の `test_T07_existing_delete_api_on_self_reference_and_cycle_is_recorded_not_relied_on`（自己参照・循環で 500）と `test_T07_a_factor_of_another_analysis_directly_below_blocks_it_and_its_ancestors`（別の分析の要因を巻き込んで 200）。ほかにもあれば専用 PR で列挙する）。
8. **今回の対策で保証しない範囲を明記**する：検査から削除までの間の並行の変更（別のワーカー・別の要求）、既存の不整合データの修復、不整合データができること自体（S-1・S-8）。

### S-12（生成 API の循環の検出）

1. **対象**：親を指定した要求と、親を指定しない二次・三次の要求の両方。
2. **自己参照・循環・走査の上限**（深さの上限）を検出し、その親については **AI を呼ばず、要因を作らずに**終える。
3. **親を指定しない要求では、不整合な親を除く**。正常な親は従来どおり対象にする。除いた結果、対象が0件になった場合の理由（例：不整合のため対象外になった件数）を応答の `message` で明確にする。
4. 応答は、**既存の生成 API の失敗の形式**（`success`、`message`、`created`・`skipped` などの件数）を基本とし、**一律に 409 には変えない**。
5. 正常な一次・二次・三次の、**通常生成・追加生成の挙動を維持**する。
6. 記述では、「**20 秒以内に応答しなかった**」という実測と、「**同じプロセスのほかの要求への影響**」というコードからの判断を区別する。「アプリ全体への影響」は、単一ワーカー（1プロセス）で動かしている場合に限ると明記する。

### 対象にしないもの

DB スキーマの変更、不整合データの自動修復、生成の並行化（S-7）、親の存在確認（S-1）・外部キー制約（S-8）・入力検査の全般（S-9）へは広げない。

### 8.3 S-11 の保証の範囲と残余リスク（検査と削除の間の並行の変更）

- **保証する範囲**：検査と削除は同じ要求・同じ DB セッションで続けて行う。削除は、(1) ORM の連鎖削除が対象にした要因の集合が、検査した範囲と一致し、(2) DELETE の実行の後（SQLite ではこの時点から確定まで書き込みのロックを持ち、ほかの接続は書き込めない）に、削除した要因を親とする要因と（分析の削除では）その分析の要因が残っていない、場合だけ確定する。検査の後、削除の前に、別の要求（別のスレッド・別のワーカー・別のタブ）が範囲の下に子を加えた、別の分析の要因を範囲の下に付けた、循環を作った、分析に要因を加えた、のいずれも、ロールバックして 409（「確認の途中で削除される範囲が変わりました。何も削除していません。画面を再読み込みしてから、もう一度操作してください。」）にする（試験：`test_S11_a_change_between_the_check_and_the_delete_is_refused`・`test_S11_a_factor_added_to_the_analysis_after_the_check_is_refused`）。
- **残余リスク**：
  1. この削除の**確定の後**に、別の要求が削除済みの要因を親とする要因を作ること（例：生成中に親が削除される。親の存在確認がない既存の問題、S-1・M-2〜M-4）は防げない。
  2. 既存の不整合データの修復はしない（対象外）。不整合データができること自体（S-1・S-8）も防げない。
  3. 「書き込みのロック」は SQLite（このアプリの DB）での前提。ほかの DB での動作は確かめていない。
  4. 並行の変更の試験は、検査の直後に別の接続で変更を確定させる注入で行った（実際の複数ワーカーでの同時実行は試していない）。
