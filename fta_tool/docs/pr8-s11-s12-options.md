## 1. 前提：どのようなデータで起きるか

S-11・S-12 は、**親子関係に不整合がある要因**（別の分析の要因を親にしている、自己参照、循環など。計画 第5.9.5節の区分）があるときだけ起きる。

- 画面と既存の API の通常の操作では、こうしたデータは作られない：手動追加（`POST /nodes/{id}/children`）は子を親と同じ分析に作り、生成は同じ分析の要因だけを親にする（`node_map` が分析内の要因だけ）。
- 起こりうる経路（いずれも未確認）：DB の直接編集、過去の版の不具合、計画 第2.4節の M-2〜M-4（並行処理の構成で、生成中に親が削除されると親のない子ができ、SQLite が削除された ID を再利用すると、その子が別の分析の要因を親として指す）。利用者の DB にこうしたデータがあるかは**未確認**（計画 第12.2節）。
- 編集画面は不整合を区分して表示し、安全性を確かめられない削除・生成をしない（PR-3、判断2・判断3）。**これは画面が取得した時点の情報による画面側の抑止で、API の安全性の保証ではない。**

## 2. 現在のコードで未解決の範囲（2026-11-02、`254f826`）

### S-11 分析をまたぐ連鎖削除と、不正な親子関係の安全な削除・修復

| 経路 | 現在の動作 | 画面の抑止 |
|---|---|---|
| **一覧からの分析全体の削除**（`POST /analyses/{id}/delete`。`main.py` の `delete_analysis` → `crud.delete_analysis`） | 分析の要因を ORM の連鎖削除（`models.py` の `Analysis.nodes` と `Node.children`、`cascade="all, delete-orphan"`）で消す。`Node.children` は分析を区別しないため、**親がこの分析の要因である別の分析の要因も削除される**（HTTP 200）。自己参照・循環の要因があると HTTP 500 で、何も消えない | **なし**。一覧の削除ダイアログ（`list.js` の `openDeleteDialog`）は件数（`crud.count_nodes_by_analysis`。この分析の要因だけ）を示すだけで、別の分析の子孫を調べない。**利用者の画面操作だけで起きる経路** |
| 編集画面の要因の削除（`POST /nodes/{id}/delete`。`crud.delete_node`） | 同じ連鎖削除で、`parent_id` でたどれる別の分析の子孫も削除する。自己参照・循環では HTTP 500 で何も消えない | あり（PR-3 判断2）：サーバーが削除範囲を走査し（`detail_view.deletion_scope`）、別の分析の要因を含む・走査を完了できない・確認用の問い合わせに失敗した場合はボタンを無効にし、ダイアログを開く時と確定の直前にも判定する。**画面の取得の後の変化（別のタブなど）と API の直接呼び出しには効かない** |
| 不正な要因の修復（親の付け替え、自己参照・循環の解消） | 画面にも API にも手段がない | 自己参照・循環・別分析への親参照・階層不一致の要因は、編集画面から削除できない（判断2-4） |

### S-12 生成 API の循環の検出

| 経路 | 現在の動作 | 画面の抑止 |
|---|---|---|
| 親を指定した生成（`POST /analyses/{id}/generate/level/{n}`、`parent_id` あり） | 親の経路を作るループ（`main.py` の `generate_factors` の「Build parent path」、`while current is not None:`）に、たどった要因の記録も深さの上限もない。**親が循環上にあるか循環の下にあると、ループが終わらない**。このループは `async def` の中の同期処理のため、**サーバーのイベントループを止め、同じプロセスのほかの要求にも応答しなくなる**（下の実行確認） | あり（PR-3 判断3）：不整合のある要因と「上位に不整合あり」の要因を親にしない。ボタンの無効化に加え、要求の送信の直前にも判定する（`generation.js`・`permissions.js`） |
| 親を指定しない二次・三次の生成（`parent_id` なし） | その階層の Yes の要因を**不整合の有無にかかわらず**すべて親にする。循環上の Yes の要因があれば、上と同じくループが終わらない | あり：画面は二次・三次で必ず `parent_id` を指定し、親指定なしの要求を送らない（判断3） |
| 親の階層の検査 | `parent_id` の要因の階層が「生成する階層 − 1」かを確かめない（S-9 の一部） | あり：画面は階層の合わない親を送らない |

**画面側の抑止（判断3）と API 側の循環の検出（S-12）は別のもの**である。前者は、この画面がそのような要求を送らないことを保証するだけで、API の直接呼び出し・別の画面・取得の後のデータの変化からの要求には効かない。

### 実行確認（2026-11-02、`254f826` のクリーンな worktree、一時ディレクトリの一時 DB）

アプリは変えず、テスト用のクライアント（`fastapi.testclient`）で既存の API を呼び、不整合は一時 DB に直接書き込んで作った。AI プロバイダは mock（実LLMなし）。各回は新しい一時ディレクトリ、メモリの上限 3GB、20 秒の時間制限。

| 確認 | 手順 | 結果 |
|---|---|---|
| S-11 一覧からの分析の削除 | 分析 X（一次1件）、分析 Y（一次2件、二次1件）。Y の二次の親を X の一次に書き換え、X を削除 | HTTP 200。X の要因 1 → 0、**Y の要因 3 → 2**（Y の二次が消え、Y の無関係な一次は残った） |
| S-11 要因の削除 | 同じデータで X の一次を `POST /nodes/{id}/delete` | HTTP 200。**Y の要因 2 → 1**（Y の二次が消えた） |
| S-11 循環を含む分析の削除 | 一次 A・二次 B で A の親を B に書き換え（A⇄B）、分析を削除 | HTTP 500。要因 2 件と分析は残った（何も消えない） |
| S-12 親を指定した生成 | 同じ A⇄B、両方を Yes。三次の生成を `parent_id` = B で要求 | **20 秒以内に応答なし**（時間制限で終了、終了コード 124） |
| S-12 親を指定しない生成 | 同じデータで三次の生成を `parent_id` なしで要求 | **20 秒以内に応答なし**（同上） |

計画（2026-09-29）では S-12 は「コードの確認。実行はしていない」だったが、この確認で、処理が終わらないことを一時 DB で再現した（20 秒の打ち切りまで。メモリの増え方と、最終的にどう終わるかは確かめていない）。

## 3. 2つの案

### 案1：最終統合の前に、最小限のサーバー側の対策を別の PR で行う

| 項目 | S-11 | S-12 |
|---|---|---|
| 対象箇所 | `app/crud.py` の `delete_node`・`delete_analysis`（または `app/main.py` の両ルート）。範囲の走査は `app/detail_view.py` の `deletion_scope` と同じ考え方（深さの上限なし、たどった要因を記録、要因数を超えたら中止） | `app/main.py` の `generate_factors`：親の経路のループと、親を指定しない場合の親の選び方 |
| 変更内容（最小限） | 削除の前に、削除される範囲（要因の削除はその要因と子孫、分析の削除はその分析の全要因と子孫）を走査し、(a) 別の分析の要因が含まれる、(b) 走査を完了できない（自己参照・循環）場合は**何も消さずに拒否**する（例：HTTP 409 と理由の文）。正常な範囲は従来どおり消す。修復の手段は加えない | 経路のループにたどった要因の記録と深さの上限（3）を加え、循環・上限超えを検出したら、その親を処理失敗として扱い AI を呼ばない（応答の形は変えず `success:false` と理由）。親を指定しない二次・三次は、不整合のある要因を親から除く（画面と同じ判定） |
| 正常系への影響 | 結果は変わらない。削除ごとに読み取りの問い合わせが増える（範囲の走査。要因数に比例） | 結果は変わらない（正常な木では経路は同じ）。比較の処理が増えるだけ |
| 異常系への影響 | 別の分析の要因を巻き込む削除が、200（巻き込んで削除）から 409（何も消さない）に変わる。自己参照・循環は 500 から 409（理由つき）に変わる。一覧の削除ダイアログと編集画面の削除ダイアログは、既存のエラー表示（`list.js` はサーバーの理由を「削除できませんでした：…」と表示）で理由を示せる見込み（画面の変更は不要の見込み。要確認） | 終わらない要求（サーバー全体の停止）が、すぐ返る失敗に変わる。親指定なしの要求では、不整合のある親が対象から外れる（従来は対象） |
| API 契約 | **異常時の応答が変わる**（新しい 409）。正常時の要求・応答の形は変えない。DB スキーマは変えない | 応答の形は変えない（`success:false` と `message`）。親指定なしの要求の対象の範囲が変わる |
| 必要な試験 | 通常の pytest に追加：要因の削除・分析の削除それぞれで、正常な範囲（従来どおり消える）、別の分析の子が直接・孫以下に付く（409、両方の分析が残る）、自己参照・循環（409、何も消えない）、一覧のダイアログの件数と実際の削除の一致。E2E：一覧の削除の失敗表示（E-L06 の失敗の経路を 409 で）、編集画面の削除（PR3-DELETE-SCOPE の回帰）。**通常の pytest と累積の全必須 E2E の再実行** | 通常の pytest に追加：親が循環上・循環の下・自己参照・深さの上限超えで、時間制限内に `success:false` が返り、要因が作られず、AI が呼ばれない。親指定なしで不整合のある Yes の親が除かれる。正常な一次・二次・三次の生成の回帰（`test_generate_endpoint.py`）。**通常の pytest と累積の全必須 E2E の再実行** |
| 受入への影響 | アプリのコードが変わるため、**新しい受入候補の SHA** になる。PR-7 の Windows の記録（`b118038`）は、その SHA の結果ではなくなる（画面の CSS・JS は同じだが、サーバーの処理が変わる）。Windows の Chrome・Edge の Full の再実行（各 20 分前後）の要否を利用者が判断する必要がある | 同左（S-11 と同じ PR にすれば1回の再確認で済む） |
| 残るリスク | 確認から削除までの間の並行の変更（別のワーカー・別のタブ）は防げない（同じトランザクションの中で走査・削除すれば単一ワーカーでは小さい）。既存の不整合データの修復はできない。不整合データができること自体（M-2〜M-4、S-1・S-8）は防げない | 階層の検査（S-9）・親の存在確認（S-1）は含まない。ほかの経路の走査（出力の Markdown は根からたどるため循環で止まらないことをコードで確認。不整合の要因は出力されない：従来どおり）は変えない |
| 規模の目安 | 小〜中（サーバー側の関数とその試験。画面の変更は原則なし） | 小（ループと親の選び方。試験） |

### 案2：制約・影響の条件・後続の対応の時期を明記し、利用者の判断を受けて後続の対応とする

| 項目 | 内容 |
|---|---|
| 対象箇所 | 変更しない（S-11・S-12 は別提案のまま） |
| 変更内容 | 文書だけ：README・現行仕様書（第8節）・計画書（第11節・第12.2節）に、下の「制約として明記する内容」を記録する（PR-8 で記載済み）。後続の対応の時期（例：統合の後の最初の改修の PR、S-1・S-8・S-9 と合わせて、など）を利用者が決める |
| 正常系への影響 | なし（現在の受入の対象のコードのまま） |
| 異常系への影響 | 現状のまま：不整合データがあると、一覧からの分析の削除で別の分析の要因が消える（確認なし、件数にも出ない）。API の直接呼び出しで循環上の親を指定すると、サーバー全体が応答しなくなる（再起動が必要） |
| 必要な試験 | 追加の試験はない。PR-8 の試験（通常の pytest と累積の全必須 E2E）と PR-7 の Windows の記録をそのまま受入の根拠にできる（コードが `b118038` と同じため） |
| 残るリスク | 上の異常系がそのまま残る。発生の条件は不整合データの有無（利用者の DB で未確認）と、API の直接呼び出し・複数ワーカーの構成の有無 |
| 影響を小さくする運用（任意） | (1) 統合の前に、利用者の DB の写しで不整合の有無を確かめる（読み取りだけの確認。例：`scripts/pr3_check_db.py` は PR-3 の確認用 DB を作る道具で、既存の DB の検査には使えないため、別に簡単な SQL を用意する必要がある）。(2) 単一ワーカーで起動し、API を直接呼ばない。(3) 不整合が見つかった場合は、その分析の削除の前に利用者が判断する |

制約として明記する内容（案2を選ぶ場合。PR-8 の文書には、案の判断が未決のため「未解決」として記載済み）：

1. 一覧からの分析の削除は、親がその分析の要因である**別の分析の要因も削除する**。削除の確認ダイアログの件数には入らない。不整合データがなければ起きない。
2. 要因の削除 API も同じ。編集画面は削除の前に範囲を確かめて抑止するが、画面の取得の後の変化と API の直接呼び出しには効かない。
3. 自己参照・循環の要因を含む分析・要因の削除は HTTP 500 で、何も消えない。修復の手段はない。
4. 生成 API に循環上の親を指定する（または、親を指定せず循環上の Yes の要因がある）と、要求が終わらず、サーバー全体が応答しなくなる。編集画面はそのような要求を送らない。

## 4. 比較の要点と判断事項

| 観点 | 案1（統合前に最小限の対策） | 案2（制約を明記して後続） |
|---|---|---|
| 利用者の画面操作だけで起きる被害（一覧からの分析の削除で別の分析の要因が消える） | 防ぐ | 残る（不整合データがある場合） |
| サーバー全体の停止（S-12） | 防ぐ | 残る（API の直接呼び出しなど、画面以外の要求の場合） |
| 統合までの作業 | 別の PR の実装・試験・レビュー、受入候補の SHA の更新、Windows での再確認の要否の判断 | 文書だけ（PR-8 で完了） |
| 既存の受入の証跡の使い方 | PR-7 の Windows の記録（`b118038`）は新しい SHA の結果ではなくなる | そのまま根拠にできる（コードが同じ） |
| API 契約 | 異常時の応答が変わる（409 など）。利用者の承認が必要 | 変わらない |

利用者に判断を求める点：

1. **S-11**：案1（統合前に別の PR で対策）／案2（制約として明記し後続）のどちらにするか。案1の場合、拒否の応答（409 と理由の文）でよいか。分析の削除と要因の削除の両方を対象にするか。
2. **S-12**：案1／案2のどちらにするか。案1の場合、親を指定しない要求で不整合のある親を除くこと（対象の範囲の変更）を含めるか。
3. 案1を選ぶ場合：S-11 と S-12 を1つの PR にするか。新しい受入候補での Windows の確認（Chrome・Edge の Full の再実行など）を行うか、開発環境の試験だけで受け入れるか。
4. 案2を選ぶ場合：後続の対応の時期と、統合の前に利用者の DB の写しで不整合の有無を確かめるか。

PR-8 では、どちらの案でも進められる作業（文書の更新、試験、受入の準備）を完了している。**S-11・S-12 のアプリの改修は PR-8 に含めていない。**
