# PR-3 Windows 実機確認の手順

計画書（[ui-redesign-implementation-plan.md](ui-redesign-implementation-plan.md)）第8.3節の手動確認（10項目）を、Windows の Edge・Chrome で行うための手順です。対象は **PR #18 の最新 HEAD**（PR 本文の「最新 HEAD」に書いた SHA）です。

この手順書は確認の進め方をまとめたもので、受入の合否を決めるものではありません。合否と PR #18 のマージは、利用者が判断します。

**確認の方式（2026-10-03 の利用者の判断）**：Edge は手動で確認しました（第1〜10節の手順）。Chrome は、同じ全手順を人手で繰り返さず、Windows のインストール済みの Chrome Stable で既存の E2E を自動で実行し、自動化だけでは確かめきれない表示・操作感を少数の目視で確認します。自動テストで代わりにならない部分があれば、その部分だけを手動で確認します。「Chrome でも全項目を人手で確認した」とは記録しません。

| ブラウザ | 方式 | 対象の SHA | 状態 |
|---|---|---|---|
| Microsoft Edge | 手動確認（第1〜10節） | `4b49914` | 項目1〜10、第5節、第7節の主要な操作・期待結果を確認済み（2026-10-02、利用者）。未確認・未特定の事項は第11.2節 |
| Google Chrome | 自動 E2E（第12節）＋限定した目視（第13節）。対応表は第11節 | PR #18 の最新 HEAD | 未実施。Windows 実機の結果を受けるまで、確認済みとしない |

## 0. はじめに（守ること）

- **普段の DB と作業フォルダは使いません。** PR #18 のコードは、SHA ごとの別フォルダ（git worktree）に取り出します。確認用の DB は、確認の回ごとに作る記録フォルダの中にだけ置きます。
- **ブラウザごと・再試験ごとに、新しい記録フォルダと確認用 DB を作ります**（第2節）。Edge で操作した DB を、Chrome の確認（特に初期状態の確認）に使い回さないでください。前の回の記録フォルダは消さずに残します。
- **設定と DB は、別の場所を参照します。**

  | 対象 | アプリが参照する場所 | この手順での場所 |
  |---|---|---|
  | 設定（`.env`） | コード側の `fta_tool\.env`（`--app-dir` に指定したフォルダの中） | `C:\fta-check\src-<SHA先頭7桁>\fta_tool\.env`。置かない |
  | DB（`fta_tool.db`） | サーバーを起動したときの作業フォルダの `fta_tool.db` | 記録フォルダの `normal\fta_tool.db`、`anomaly\fta_tool.db` |

- **AI は mock にし、そのことを3か所で確かめます。**
  - シェルで `$env:AI_PROVIDER = "mock"` を設定する。
  - 起動ログに `AI_PROVIDER                = mock` と出ることを確かめる。
  - 編集画面のヘッダーに「AI: mock」と出ることを確かめる。

  コード側に `.env` があると、その値がシェルの設定より優先されます（`override=True`）。このため、コード側に `.env` がないことも確かめます。`.env` がないことだけでは mock の確認にしません。
- **不整合データは、確認用の不整合 DB にだけ作ります。** 普段の DB には作らないでください（計画 第8.3節）。
- **通知が示す結果は3通りに分けて記録します**（第6節）。
  - 送信前の入力検査で止まった：操作は行われていない。
  - 成功を確認した後の表示の更新の失敗：操作は完了している。
  - 通信の切断などで結果を確認できない：成否不明。直ちに同じ操作を送り直さない。
- **F5（再読み込み）の前に、未保存の入力を保存するか退避します。** ① の頂上事象・参考情報、ヘッダーのタイトル、開いているダイアログの入力は、F5 で失われます。
- ブラウザは、Windows 11 の Edge と Chrome を使います。表示倍率 100%、ブラウザの拡大 100%、ウィンドウは最大化します（項目 7 は開発者ツールで寸法を指定します）。

```text
C:\fta-check\
  src-24f558b\                       PR #18 のコード（SHA ごとの git worktree）
    fta_tool\                        ← $src。.env はここを見る（置かない）
  runs\
    24f558b-20260930-1500-edge\      ← $run。確認の回（ブラウザ・再試験）ごとに新しく作る

```

## 1. PR #18 の最新 HEAD を取り出す

PowerShell で、普段のリポジトリのフォルダから実行します。普段のフォルダの作業中の変更には触れません。`<SHA>` には、PR #18 本文の「最新 HEAD」の40桁の SHA を入れます。

```powershell
cd C:\work\fta-202605                            # 普段のリポジトリ（例）
git fetch origin claude/intelligent-noether-fcntpc
git ls-remote origin refs/pull/18/head           # PR #18 の head の SHA
$sha = "<SHA>"
$wt  = "C:\fta-check\src-$($sha.Substring(0,7))"
git worktree add --detach $wt $sha
git -C $wt rev-parse HEAD
git -C $wt status --short
Test-Path "$wt\fta_tool\.env"
```

確認すること:

- `git -C $wt rev-parse HEAD` の SHA が、`$sha`（PR #18 本文の「最新 HEAD」）と `git ls-remote` の SHA の両方と一致すること。
- `git status --short` が何も表示しないこと。
- `Test-Path "$wt\fta_tool\.env"` が `False` であること（コード側に `.env` がない）。

一致しない場合は、確認に進まずに報告してください（PR に新しいコミットが入った可能性があります）。PR の SHA が変わって再試験するときは、新しい SHA で同じ手順を行い、別の worktree を作ります（前の worktree と記録は残します）。

## 2. 確認の回ごとの準備（ブラウザごと・再試験ごと）

### 2.1 PowerShell を開いたら、最初に行う設定

**新しい PowerShell を開くたびに**、次を実行します。`$run` は、その回の記録フォルダです。最初の窓では 2.2 で作るので、この行は飛ばします。2つ目以降の窓では、2.2 で表示された名前をそのまま書きます。

```powershell
$py  = "C:\work\fta-202605\fta_tool\.venv\Scripts\python.exe"   # 普段アプリを起動している python.exe（例）
$sha = "<SHA>"                                                   # 確認する SHA（40桁）
$src = "C:\fta-check\src-$($sha.Substring(0,7))\fta_tool"        # PR #18 のコード。.env はここを見る
$run = "<この回の記録フォルダ>"                                    # 2つ目以降の窓だけ。例：C:\fta-check\runs\24f558b-20260930-1500-edge
$env:AI_PROVIDER = "mock"                                        # AI は mock
Test-Path "$src\.env"                                            # False であること。True なら中止して報告
```

Python は、普段アプリを起動しているもの（仮想環境）をそのまま使えます。PR-3 では `requirements.txt` を変えていません。

### 2.2 記録フォルダと確認用 DB を作る

ブラウザごと（Edge の回・Chrome の回）と再試験ごとに、**新しい**記録フォルダを作ります。前の回のフォルダは、消さずに残します。

```powershell
$run = "C:\fta-check\runs\{0}-{1}-edge" -f $sha.Substring(0,7), (Get-Date -Format "yyyyMMdd-HHmm")   # Chrome の回は末尾を chrome に
Test-Path $run                                   # False であること（既存の記録に上書きしない）
& $py "$src\scripts\pr3_check_db.py" normal  "$run\normal"
& $py "$src\scripts\pr3_check_db.py" anomaly "$run\anomaly"
New-Item -ItemType Directory -Path "$run\logs", "$run\screenshots" | Out-Null
$run                                             # 表示された名前を控える（別の窓の $run に使う）
```

期待結果（正常データの DB）:

```text
作成しました：C:\fta-check\runs\24f558b-20260930-1500-edge\normal\fta_tool.db
  分析 ID 1：PR3確認：要因なし
  分析 ID 2：PR3確認：三次まで
```

不整合 DB では、「PR3確認：不整合」「PR3確認：別の分析」と出ます。

このスクリプト（`scripts/pr3_check_db.py`）は、**新しいフォルダか空のフォルダにだけ** DB を作ります。何かが入っているフォルダを指定すると「中止しました：フォルダが空ではありません」と出て、何も変更しません。既存の DB を上書きしたり、フォルダを削除したりする機能はありません。やり直すときは、新しい記録フォルダを作ります。

| 階層 | 要因 | 評価など |

| 一次（20件） | 一次01 決済APIの応答遅延 〜 一次20 担当者の操作ミス | Yes：一次01〜03、No：一次04、ほかは未評価。一次01 は説明・メモ・根拠・再発防止策が長め |

## 3. 確認用サーバーを起動し、mock であることを確かめる

2.1 の設定を済ませた PowerShell で実行します。作業フォルダ（`-WorkingDirectory`）を記録フォルダの `normal` にするので、DB は `$run\normal\fta_tool.db` を使います。コードは `--app-dir` の `$src` から読み、設定（`.env`）もそこを見ます。ログは `$run\logs` に保存されます。

```powershell
$normal = Start-Process -FilePath $py -PassThru -NoNewWindow `
  -ArgumentList @("-m", "uvicorn", "app.main:app", "--app-dir", ('"{0}"' -f $src), "--host", "127.0.0.1", "--port", "8001") `
  -WorkingDirectory "$run\normal" `
  -RedirectStandardOutput "$run\logs\normal-stdout.log" -RedirectStandardError "$run\logs\normal-stderr.log"
Start-Sleep -Seconds 5
Select-String -Path "$run\logs\normal-stderr.log" -Pattern "dotenv file not found", "AI_PROVIDER", "Uvicorn running"
```

起動ログで確認すること（3行とも出ること）:

- `dotenv file not found at C:\fta-check\src-<SHA先頭7桁>\fta_tool\.env`（コード側の `.env` を読んでいない）。
- `AI_PROVIDER                = mock`。
- `Uvicorn running on http://127.0.0.1:8001`。

3行がまだ出ていないときは、数秒待ってから `Select-String` をもう一度実行します。`AI_PROVIDER` が `mock` 以外のとき、または `dotenv loaded:` と出たとき（コード側の `.env` を読んでいる）は、すぐにサーバーを止めて（下記）報告してください。

画面で確認すること:

1. 前の回のタブをすべて閉じてから、新しいタブで `http://127.0.0.1:8001/` を開く（画面の状態はタブごとの sessionStorage に保存されるため）。
2. 分析の一覧が「PR3確認：三次まで」「PR3確認：要因なし」の2件だけであること。普段の分析が見える場合は、すぐにサーバーを止める（DB の場所が違う）。
3. 分析を開き、編集画面のヘッダーに「AI: mock」と出ること。

サーバーの止め方:

```powershell
Stop-Process -Id $normal.Id
# 起動した窓を閉じてしまった場合（ポート 8001 で待ち受けているプロセスを止める）
Get-NetTCPConnection -LocalPort 8001 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess }
```

## 4. 10項目の手順と期待結果

特に書いていない限り、「PR3確認：三次まで」を使います。分析は一覧から開きます。URL に `#` 以降が付いていない状態から始めてください。

### 項目1 既定の表示

1. 一覧で「PR3確認：要因なし」を開く。

### 項目2 全経路からの選択と、表示の一致

次の経路で要因を選びます。毎回、構造ナビ・作業リスト・ツリー・一覧表・インスペクタで同じ要因が選ばれていること、作業ステップがその要因の階層（一次→②、二次→③、三次→④）に切り替わることを確認します。ツリーと一覧表は、表示タブ「ツリー」「一覧表」で見ます。

| 作業リストの行 | ④ の作業リストで「三次01-2-1 ライブラリの既定設定」の要因名を押す | 三次01-2-1 |

### 項目3 評価の変更と、全表示・件数

1. ② で「一次05 認証トークンの期限切れ」（未評価）の「Yes」を押す。
   - 通知「評価を更新しました」が1回出る。
   - ② の件数が「20件・未評価16」から「20件・未評価15」になる。
   - ③ の操作バーが「生成の対象：Yesの一次要因 3件」から「4件」になる。
   - 構造ナビ・作業リスト・一覧表・インスペクタの評価が「Yes」になる。
2. 「ツリー」タブで、一次05 の評価が「Yes」になっている（C-04：再読み込み前から反映）。
3. インスペクタの評価ボタンで同じ要因を「未」に戻し、同じように全表示と件数が戻ることを確認する。

### 項目4 絞り込み

1. 絞り込み欄（「要因名・説明で絞り込み」）に「タイムアウト」と入力する。
   - 件数表示が「一致 2件（全37件）」（一次01 は説明、二次01-1 は要因名が一致）。
   - 作業リスト（② では一次01 だけ）と一覧表では、一致しない要因が隠れる。
   - 構造ナビとツリーでは要因は隠れず、一致する要因が強調され、ほかは薄く表示される。
2. 「クリア」を押し、評価の選択で「Yesのみ」「Noのみ」「未評価のみ」「要確認のみ」を順に選ぶ。
   - 同じく、作業リスト・一覧表は隠れ、構造ナビ・ツリーは強調になる。
   - 「要確認のみ」では二次01-2 だけが一致する。
3. 最後に「クリア」を押す。

### 項目5 再読み込みでの復元

1. ① などに未保存の入力がないことを確かめる（あれば、保存するかメモ帳などに退避する。F5 で失われる）。
2. 「一覧表」タブで「二次02-1 在庫数の同時更新」を選び、構造ナビを少しスクロールし、絞り込み欄に「在庫」と入力する。
3. F5 を押す。
   - 同じ要因が選ばれ、③・「一覧表」タブ・スクロール位置・絞り込み（「在庫」）が戻る。
4. 絞り込みを「クリア」する。

### 項目6 旧モーダルでの操作と、再読み込みなしの反映

再読み込みされていないことは、① の未保存の入力が残ることで確かめます。

1. ① の「頂上事象」欄の末尾に「（未保存の入力）」と入力し、**保存せずに** ② に戻る。
2. 詳細の保存：「一次05」を選び「詳細を編集」→ メモに「手動確認で保存したメモ」と入力 →「保存」。
   - 通知「保存しました」。インスペクタの詳細にメモが出る。
3. 手動追加：② の「手動追加」→ タイトル「一次21 手動確認で追加した要因」→「追加」。
   - 通知「要因を追加しました」。追加した要因が選ばれ、② の件数が「21件…」になる。
4. 削除：追加した「一次21 手動確認で追加した要因」を選び、「この要因を削除」を押す。
   - 確認ダイアログ「要因「一次21 手動確認で追加した要因」を削除しますか？ この要因の子要因もすべて削除されます。この操作は取り消せません。」で OK を押す。
   - 通知「削除しました」。選択は頂上事象に移る（一次要因を削除したため）。
5. ① に戻り、「頂上事象」欄に「（未保存の入力）」が残っていること（全体が再読み込みされていない）を確認する。入力は元に戻しておく（保存しない）。

### 項目9 旧処理の通知と、旧ダイアログ表示中の通知の位置

1. 通知が出る場所が1か所であること：保存（項目6）・生成（下の3）・削除（項目6）の通知は、画面下部の中央の通知欄に、1回ずつ出る。右下に古い形式の通知は出ない。成功の通知は自動で消える。

## 5. 別のタブで評価を変えた後の復帰（既知事項の確認）

## 6. 通知が示す結果の区別と、成否不明のときの確かめ方

操作の後に出る通知は、次のように分けて記録します。**「通信エラーが発生しました」などを、一律に「保存・追加・削除されていない」とは扱いません。**

| 区分 | 主な通知 | 保存・追加・削除など | 対応 |
|---|---|---|---|
| 送信前の入力検査で止まった | 「要因タイトルは必須です」「タイトルを入力してください」「タイトルは必須です」「タイトルは255文字以内で入力してください」「頂上事象を入力してから生成してください」「Yes評価の要因がありません」、親や削除の判定で止めたもの（「…追加・生成できません。」「…この画面では削除できません。」など） | **行われていない**（要求を送っていない） | 入力や選択を直して、やり直す |
| 送信した後、サーバーが理由を返して処理しなかった | 「保存に失敗しました」「追加に失敗しました」「削除に失敗しました」「分析コンテキストの保存に失敗しました」、サーバーの理由をそのまま示すもの（例：「評価を保存できませんでした：ノードが見つかりません」） | **行われていない**（サーバーが処理を断った応答を受け取っている） | 理由を確認する。分からなければ、下の「成否不明」と同じように保存済みのデータを確かめてから判断する |
| 成功を確認した後の、表示の更新の失敗 | 「表示を最新にできませんでした。ページを再読み込みしてください。」「最新の表示に更新できませんでした（理由）。入力中の内容を保存してから、ページを再読み込みしてください。」。入力中の内容がないときは、通知なしで自動的に再読み込みされる | **完了している**（直前に「保存しました」「要因を追加しました」「削除しました」などが出ている）。表示だけが反映されていない | 未保存の入力を保存または退避してから F5。次の部分更新でも反映される（第5節） |
| 通信の切断や、応答の読み取りの失敗で、結果を確認できない | 「通信エラーが発生しました」、「評価を保存できませんでした：サーバーに接続できませんでした（通信エラー）」「…：サーバーの応答を読み取れませんでした」「…：サーバーでエラーが発生しました（HTTP 500 など）」 | **成否不明**（要求がサーバーに届いて処理されたかどうかを、画面は確認できていない） | **同じ操作を直ちに送り直さない**。下の手順で保存済みのデータを確かめてから判断する |
| 生成の失敗 | 「生成に失敗しました」「追加生成に失敗しました」「一部でエラーが発生しました: …」「エラーが発生しました」、親グループの見出しの「エラー」 | **一部の要因が作られている場合がある**（生成 API は、失敗を返すときも途中までに作った件数を返す） | 成否不明と同じく、直ちに送り直さない。要因ができているかを確かめてから判断する（送り直すと重複することがある） |
| 分析が見つからない | 「分析が見つかりません（削除された可能性があります）」 | 分析が別の画面で削除されている | 一覧へ戻る |

**成否不明のときの確かめ方**（アプリには自動の再試行はなく、この手順で確かめます）:

1. 同じ操作（保存・追加・削除・生成・評価）を、直ちにもう一度押さない。いま開いているタブは、そのままにする（未保存の入力が残る）。
2. 新しいタブで一覧（`http://127.0.0.1:8001/`）を開き、同じ分析を開く。新しいタブは、サーバーに保存されている内容を表示する。
3. 新しいタブで、対象を確かめる。
   - 詳細の保存：その要因を選び、インスペクタの詳細（メモなど）を見る。「詳細を編集」を開いた場合は、保存せずに「キャンセル」で閉じる。
   - 手動追加：追加した名前の要因があるか。
   - 削除：その要因がなくなっているか。
   - 評価：その要因の評価。
   - 頂上事象：① と構造ナビの頂上事象。
   - 生成：親の下に新しい要因ができているか。同じ生成を送り直すと、要因が重複することがある。
4. 判断する。
   - 反映されていた：送り直さない。元のタブは、未保存の入力を保存または退避してから F5 で最新にする。
   - 反映されていなかった：元のタブで、同じ操作を1回だけやり直す。
   - もう一度同じ通知が出た、または判断できない：そこで止めて、通知の文言・時刻・確かめた内容と、`$run\logs` のログを記録する。

「ノード情報の取得に失敗しました」は、詳細ダイアログを開くための読み取りの失敗で、何も変更していません（開き直してかまいません）。

表示の更新の失敗や成否不明の通知が出たときは、直前の通知と、確かめた結果（保存されていたか）を記録してください。

## 12. Windows の Chrome での自動確認（E2E）

手順は「初回準備（12.3）→ 準備確認（12.4）→ 全件の自動確認（12.5）→ 少数の目視確認（第13節）」の順です。

### 12.1 しくみと守ること

- 自動確認専用の venv を、通常の `.venv` とは別の場所に作り、`requirements-dev.txt` の固定版（Playwright 1.56.0、pytest-playwright 0.7.1）だけを入れます。通常の `.venv` には何も入れません。ブラウザは入れません（`playwright install chrome` は、Playwright の文書のとおり既存のインストールを上書きするため使いません）。
- インストール済みの Google Chrome（Stable）を `--browser-channel chrome` で、画面を表示して（`--headed`）起動します。プロフィールは起動のたびに作られる一時プロフィールで、通常のプロフィール・ログイン状態・Cookie・拡張機能は使いません（企業のポリシーは適用されることがあります）。Chrome が見つからない・起動できない場合は失敗として止まり、同梱の Chromium には切り替えません。
- テスト用サーバーは、記録フォルダの中の一時領域（`pytest-tmp`）に一時 DB を作り、空いているポート（8000〜8002 は使わない）で起動します。テストごとに DB を空にします。普段の DB、手動確認の DB・ログ・画像、8001・8002 のサーバーには触れません。不整合データもこの一時 DB にだけ作ります。テスト用サーバー（同じ PC の 127.0.0.1）への接続には、プロキシの設定を使いません（設定は変更しません）。
- 実LLMは呼びません。テスト用サーバーは AI の設定を `e2e-stub` に固定し、実プロバイダの取得と外部への通信を遮断し、試みがあればテストを失敗にします（画面のヘッダーは「AI: e2e-stub」）。これは、手動確認の「AI: mock」（第3節）とは別の起動方法です。シェルの `AI_PROVIDER` は使いません。コード側に `.env` がある場合、スクリプトは実行せずに止まります。
- 並列にせず、通常の速度で順に実行します。`-SlowMo` は失敗の調査用です。
- 実行中は Chrome のウィンドウが開いたり閉じたりします。見続ける必要はありませんが、テストのウィンドウをクリックしたり、キーを押したりしないでください。PC がスリープすると止まります。所要時間は、この開発環境（Linux）で約4分でした。Windows で画面を表示する実行では、それより長くかかる見込みです。

### 12.3 初回準備（1回だけ）

```powershell
& $ps1 -Mode Setup -Venv $venv -BasePython "C:\work\fta-202605\fta_tool\.venv\Scripts\python.exe"
```

- `-BasePython` は venv を作る元の python.exe です（通常の `.venv` の python.exe でよい。その `.venv` は変更しない）。
- 新しいフォルダに venv を作り、`requirements-dev.txt` の固定版を入れ、入った版と、見つかった Chrome・Edge の場所と版を表示します。既にあるフォルダ（このスクリプトで作った venv 以外）やコードのフォルダの中には作りません。
- `pip` が失敗した場合（プロキシなど）は、設定を変更せずに報告してください。
- 版の互換性：Playwright 1.56.0 は Chromium 141 の時期の版です。Playwright の文書は「その時点の Stable・Beta のチャンネルに対応する」としており、それより新しい Chrome（例：154）は文書の対象外です。この開発環境（Linux）では、Microsoft Edge 154（Chromium 154）で全必須 E2E を実行し、すべてのテストの操作と期待結果が成り立ちました（`5169534` では失敗は 12.8 の favicon だけ。その後の結果は PR #18 の本文）。これは Linux の Edge での検証で、Windows の Chrome の結果の代わりにはなりません。Chrome の起動や操作で互換性の問題が出た場合は、依存の更新やブラウザのダウングレードはせずに、記録を渡してください。根拠を付けて対応案を出します。

### 12.4 準備確認

```powershell
& $ps1 -Mode Preflight -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 実行の前に、コードの HEAD が `$sha` と一致し未コミットの変更がないこと、コード側に `.env` がないこと、Chrome が見つかること、venv が使えることを確かめ、`$out` の下に新しい記録フォルダ（`<SHA7桁>-<日時>-chrome-preflight`）を作ります。どれかを満たさないときは、理由を表示して止まります（終了コード 9）。
- 編集画面を開いて主要な要素を確かめる既存のテスト（E-E01 の2件と PR3-LAYOUT、計7件）だけを実行します。Chrome の起動、テスト用サーバー、テストデータ、終了までが成り立つかの確認で、**全必須 E2E の合格ではありません**。スキップや0件は失敗です。
- 成功の条件：判定「成功」、終了コード 0、「起動したブラウザ」が「Google LLC …」。
- favicon の 404 は、12.8 の条件に一致するものだけを既知の例外として除き、`e2e-report.md` に件数と内容を書きます（件数は決まった数ではありません）。成功の条件は変わりません。ほかに失敗があれば判定は「失敗」です。そのときは全件の自動確認に進まずに、結果（12.6）を渡してください。
- 失敗が最初の画面遷移（`page.goto` の時間切れ）で止まっている場合は、全件を再実行せずに、12.10 の診断で止まる場所を記録します。

### 12.5 全件の自動確認（準備確認が成功してから）

```powershell

```

- 全必須 E2E（`pytest -m e2e --e2e-required`）を、準備確認と同じ確認の後に実行します（記録フォルダ `<SHA7桁>-<日時>-chrome-full`）。
- 合格の条件：判定「合格」（`REQUIRED_IDS` のすべての受入項目が成功し、失敗・スキップ・未実施が0件）、終了コード 0。テストの件数は確認する SHA で決まるため、件数そのものは条件にしません（`4b49914` の時点は 155 件、`5169534` は 169 件、favicon の既知の例外の境界のテストを足した後は 171 件）。
- 一部のファイルだけを実行した結果を、全必須 E2E の合格とはしません。
- 既知の例外（favicon の 404、12.8）として除いたものは、件数と内容を `e2e-report.md` に書きます。合格の条件は変わりません。

- trace は、手元でだけ開けます（任意）：`& "$venv\Scripts\python.exe" -m playwright show-trace -h 127.0.0.1 -p 0 "<記録フォルダ>\failures\<テスト>\trace.zip"`（既定のブラウザで開き、Ctrl+C で終了）。trace を外部のサイトに読み込ませないでください。
- テストの失敗を再実行で消さないでください。再実行するときは新しい記録フォルダで行い、前の記録も残して渡してください。環境の制約（ポリシー、拡張機能、ダウンロードの制限、プロキシなど）とアプリの不具合の切り分けは、渡された記録で行います。
- 実行中に Ctrl+C で止めた場合、pytest がブラウザとテスト用サーバーを閉じます。スクリプトは、この実行で起動したプロセス（pytest の子孫で作成時刻も一致するもの）が残っていれば止め、`run-info.md` に書きます。名前やポート番号でほかのプロセスを止めることはしません。

### 12.8 既知事項：favicon の 404（2026-10-03 の判断：検証条件の限定変更）

画面を表示して実行すると、ブラウザはページを最初に開いたときに、アプリの `/favicon.ico` を自動で要求します。アプリには favicon がないため 404 になり、コンソールに「Failed to load resource: the server responded with a status of 404 (Not Found)（http://127.0.0.1:<ポート>/favicon.ico）」が出ます。`5169534` までは、自動テストがこれをコンソールのエラーとして、テスト用サーバーごとの最初のテストを失敗にしていました（Linux の Edge 154 で、準備確認1件・全件3件。この結果は書き換えずに残しています）。PR-3 より前からの状態です。

利用者の判断（2026-10-03）で、アプリ（共通テンプレート・favicon の経路）は変えずに、次のすべてを満たすコンソールのエラーだけを既知の例外として除き、別に記録します。favicon の不具合を直したものではありません。

- 文が「Failed to load resource: the server responded with a status of 404 (Not Found)」と一致し、発生元の URL が、そのテストで使っているサーバーの `<オリジン>/favicon.ico` と一致する（クエリ付き・別のパス・別のオリジンは対象外）。
- ブラウザの記録（CDP の Log）に、そのエラーと同じ文・URL の記録が、同じ順に1件ずつある。
- その記録の要求の応答（CDP の Network）が、同じ URL・状態 404・種類 Other（ブラウザ自身の要求）である。ページの fetch・画像・script による `/favicon.ico` の読み込みは対象外。
- 500 や通信の失敗、発生元の分からないエラー、ほかの 404、ブラウザの記録がそろわない場合（CDP を使えない場合を含む）は、これまでどおり失敗です。ページの例外と外部への通信の確認は変えていません。
- 除いたものは、`e2e-report.md` の「既知の例外として除いたコンソールのエラー」に、テスト名・URL・元のメッセージ・応答（要求の ID）を1件ずつ書きます。件数は実測で、決まった数ではありません。
- favicon の実装と、この除外の廃止は PR-7 です。アプリが favicon を宣言するか `/favicon.ico` に応答するようになると、通常の pytest の確認（`tests/test_e2e_infrastructure.py`）が失敗し、除外を残したままにはできません。

### 12.9 後片付け

自動確認の記録フォルダと venv は、受入の判断が終わるまで残してかまいません。終わってから消す場合は、第9節と同じく、対象を `Remove-Item -Recurse <フォルダ> -WhatIf` で確かめてから1つずつ消します。自動確認は、終わったときにテスト用サーバーとブラウザを閉じるため、止めるサーバーはありません。

### 12.10 最初の画面遷移で止まったとき：最初の読み込みの診断（-Mode Diagnose）

2026-10-05 の Windows の Chrome での準備確認（`b8b09b0`）は、7件とも最初の `page.goto`（編集画面）が 10 秒で時間切れになり、ページは `about:blank` のまま、要求に応答の記録がなく、失敗時の画面も残りませんでした（記録は書き換えずに残しています）。その記録だけでは原因が分からないため、次の診断で、同じ一時サーバーの同じ URL が「どこで止まるか」を記録します。**診断です。合否は判定しません。** テストの全件は再実行しません。

```powershell
& $ps1 -Mode Diagnose -Venv $venv -OutRoot $out -ExpectedSha $sha
```

- 準備確認と同じ確認（SHA・未コミットの変更・コード側の `.env`・Chrome・venv）の後、新しい記録フォルダ（`<SHA7桁>-<日時>-chrome-diagnose`）を作り、`tests/e2e/diagnose_navigation.py` を実行します。診断を含まない SHA のコードでは止まります（終了コード 9）。所要時間は、止まらなければ1〜2分、止まる場合は10分ほどかかることがあります（30 秒ごとに、進んでいる段階を表示します）。
- 新しい一時サーバー（新しい一時 DB と空いているポート。8000〜8002 は使わず、前回の 52750 も決め打ちしない）を1つ起動し、同じ URL を次の順に開きます。
  1. Python（httpx。プロキシの設定を使わない）から `GET /` と `GET /analyses/<id>`：状態・時間・HTML が返ったか。
  2. Playwright で起動した Chrome（headed）：最小の構成（trace・ページの監視なし）と、テストと同じ構成（trace とページの監視（CDP）あり）で、新しいコンテキストごとに「編集画面 → 一覧 → 編集画面」を開きます。要求・応答・失敗・`page.url`・commit／DOMContentLoaded／load に届いた時間と、画面（撮れなかったときは理由）を記録します。どこまで進むかを見るため、commit まで、各コンテキストの最初の読み込みは 60 秒（新しいコンテキストは、最初の要求の前にプロキシの設定（自動検出・PAC）を準備することがあるため）、ほかは 30 秒、DOMContentLoaded・load は各 15 秒まで待ちます（テストの 10 秒は変えていません）。2つの構成で結果が違うときは、ページの監視だけ・trace だけの構成も試します。
  3. 最小の構成で最初の読み込みが止まった場合だけ、Playwright が既定で付ける `--no-sandbox` を外した起動（Chrome のサンドボックスあり）でも1回開きます。
  4. Playwright を使わずに、インストール済みの Chrome を新しい一時プロフィールで起動し、同じ URL を開きます（最長 60 秒。終わったら、この診断が起動したプロセスだけを閉じ、一時プロフィールを消します）。新しいプロフィールの通常の起動のため、Chrome が Google の更新確認などの通信をすることがあります。
  5. テスト用サーバーが、この診断の間だけ、要求ごとに受信・応答の開始（状態）・応答の終了（バイト数）・相手の切断を記録します（メソッド・パス・時刻と、User-Agent の種類・接続元のポート番号だけ。クエリ・ヘッダー・本文・Cookie は記録しない）。
  6. ブラウザの通信の記録（NetLog）を取り、テスト用サーバーへの要求について、プロキシの判定（自動検出・PAC の準備の待ちを含む）、ローカルネットワークへのアクセスの確認、接続、どの段階で待っていたかを要約します。
  7. Windows の設定は読み取るだけです：プロキシの設定が「あるか」（値は記録しない）と、Chrome のポリシーの名前（値は記録しない）。
- 企業のポリシー・プロキシ・ファイアウォール・Chrome のセキュリティ機能・実行ポリシーは変更しません。通常の Chrome のプロフィールも使いません。
- 終了コード：0 診断を実行した（結果は記録にある。合否ではない）、1 続けられなかった・中断された（理由は記録にある）、9 実行前の確認で中止。
- 渡すファイル：記録フォルダの `diagnose\diagnose-report.md`（必須）、`diagnose\diagnose.json`、`diagnose\server-access.jsonl`、`run-info.md`、`diagnose-output.log`、`diagnose-stderr.log`。画面（`diagnose\screen-*.png`）と `diagnose\trace-tests.zip` は任意です。`diagnose\netlog-raw\` の原本は、ほかのサイトの URL やプロキシの設定を含むため、依頼があるときだけ渡してください（要約は `diagnose-report.md` にあります）。
- 「見立て」の行は、記録を規則で分類したもので、原因の確定ではありません。診断の後は、渡された記録で原因を切り分けてから次の手順を決めます。診断の結果で、準備確認・全件の自動確認を合格にはしません。
