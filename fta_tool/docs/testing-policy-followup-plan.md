## 1. 目的

1. 方針 第10.2節の5課題を、全必須 E2E の合格条件（`REQUIRED_IDS`・合格の条件・終了コードの意味。方針 第2.5節・第3.3節）を変えずに実装するための、順序・PR 分割・設計・試験・受入を決める。

3. 各実装 PR の利用者の作業（Windows の C など）を前もって示し、細分化による同じ試験の繰り返しと、まとめすぎによるレビュー・原因の切り分けの難しさを比べて分割を選ぶ。

## 4. 優先順位・依存関係・PR 分割

### 4.1 優先順位

1. **段階1（判定・表示・選定の記録）**：誤解を招く「不合格」の表示と、スキップ・0 件で終了コードが 0 になる部分実行の危うさを、pytest の実行そのもので解消する。段階2・3はこの記録形式を前提にする。
2. **段階2（Windows の部分実行のモード）**：手作業の実行前の確認・環境変数の解除・件数の見比べを自動化する。段階1の判定と選定の記録を使う。
3. **段階3（記録の雛形の生成）**：段階1・2の記録から事実を転記する補助。利便性の改善で、誤った合否の表示を直すものではないため最後。
4. **調査 T**：段階1の Windows の C（次の Windows の C）に T1 を相乗りさせる。T2 は T1 の結果と利用者の判断で行う。段階の完了条件にはしない。

### 4.2 依存関係

```text
段階1（acceptance.py・conftest.py：区分・判定・表示・選定の一覧と照合）
  └─▶ 段階2（run_browser_e2e.ps1：部分実行のモード。段階1の区分・照合のオプションを呼ぶ）
        └─▶ 段階3（転記補助。段階1・2の e2e-report.md・run-info.md・選定の一覧を読む）
調査 T1 ── 段階1の Windows の C（Full）に相乗り ──▶ T2（条件つき）──▶ T3（報告・扱いの判断）
```

- 段階3は段階1の記録形式だけでも作れるが、Windows の部分実行の記録（`run-info.md` の照合の結果）を転記するには段階2が要る。段階2の後に行う。
- 段階2を先に行うと、スクリプトが現行の「不合格」の判定を読み替える処理を持つことになり、段階1で作り直しになる。段階1を先にする。

| 実装 PR | 内容 | 主な変更ファイル（候補） | 方針の判断表 |

## 5. 設計事項

この章の名前・形式はすべて**設計案／未実装**。既存の名前は「既存」と書く。

### 5.1 実行の区分と判定（段階1：10.2 の1・2）

#### 5.1.1 実行の区分

| 区分 | 条件（設計案） | 判定の値（`| 判定 |` の値） | 終了コードの責任 |
|---|---|---|---|
| 全必須 E2E（既存） | `--e2e-required` または `FTA_E2E_REQUIRED` | 「合格」／「不合格」（**変えない**） | 既存のまま（不合格なら 0・5 を 1 に） |
| 準備確認（既存） | `--e2e-preflight` | 「成功（準備確認。…）」／「失敗（準備確認。…）」（**変えない**） | 既存のまま |
| 選定実行（設計案） | 新しいオプション `--e2e-selected`（設計案／未実装） | 「選定範囲：成功」／「選定範囲：失敗（理由）」。値は「合格」「成功」で**始めない** | pytest 側が保証（第5.1.4節） |
| 通常の実行（E2E を含む） | 上のどれでもなく、E2E が1件以上収集された | 「判定なし（通常の実行）」 | pytest の既定のまま（変えない） |
| E2E 対象外 | 上のどれでもなく、収集された E2E がすべて `-k`・`-m` で除外された | 「判定なし（E2E は対象外）」 | pytest の既定のまま |
| 収集のみ | `--collect-only`（pytest の `config.option.collectonly`。属性名は実装で確認） | 「判定なし（収集のみ。実行していません）」 | 必須＋収集のみは既存どおり 1（緩めない）。それ以外は pytest の既定のまま |

- **選定実行を明示のオプションにする理由**：自動で区分すると、ブラウザのない環境で `pytest` を実行しただけでスキップが失敗になり、通常の開発の終了コードが変わる。選んだ範囲を厳しく判定するのは、利用者が「A・B としてこの範囲を確かめる」と宣言した実行だけにする。
- **通常の実行の判定を「不合格」から「判定なし」に変える**：通常の実行の判定は終了コードに影響したことがなく（`on_session_finish()`）、読み取り側（`run_browser_e2e.ps1`）は通常の実行を起動しない。変えても既存の合否の扱いは変わらない。旧形式の記録（判定「不合格」）は書き換えず、方針 第5.6節の読み方の対象として残す。

#### 5.1.2 競合の扱い

| 指定 | 扱い（設計案） |
|---|---|
| `--e2e-required` ＋ `--e2e-selected` | `pytest.UsageError`（終了コード 4）。部分の指定で全必須の条件を弱めない |
| `FTA_E2E_REQUIRED=1` ＋ `--e2e-selected` | 同じく `UsageError`。メッセージで環境変数の解除を求める（既存の準備確認と同じ扱い） |
| `--e2e-preflight` ＋ `--e2e-selected` | `UsageError` |
| `--e2e-required` ＋ `-m "not e2e"` | **全必須 E2E のまま**（全項目が未実施で「不合格」、終了コード 1）。E2E が選ばれなかったことを理由に「対象外」に読み替えない |
| `--e2e-selected` ＋ `-m "not e2e"` | 選定実行で E2E が 0 件 → 「選定範囲：失敗（0 件）」 |

#### 5.1.3 選定範囲の定義と数え方

- **選定範囲**：選定実行で、収集と `-k`・`-m` の後に残った E2E の nodeid の集合（`on_collection_finish()` の `session.items` の E2E）。パラメータ展開後の nodeid（寸法を含む。例 `tests/e2e/test_edit_pr4_layout.py::test_PR4_new_controls_are_visible_and_not_covered[chrome-1905x945]`）を単位にする。
- **範囲外**：`-k`・`-m` で除外された E2E（`run.deselected`）と、コマンドで指定しなかったファイルの E2E（収集されないため数えない）。選定実行では「未実施」と数えず、「範囲外（除外 K 件）」と別に書く。
- **選定範囲内の未実施**：選定範囲の nodeid のうち結果がないもの（中断、`-x`・`--maxfail` による打ち切りなど）。**失敗として扱う。**
- 数え方は既存の `TestRecord`（nodeid ごとに1件）を使い、setup・call・teardown を別のテストとして数えない。pytest の要約行（例：`1 passed, 1 error` は同じテストの call の成功と teardown のエラー）から件数を数えない。
- 受入項目（ID）：選定実行の記録では、ID ごとに「選定内 N 件（寸法の一覧）：成功 N」または「範囲外」と書き、**ID の結果を「成功」と表示しない**。注記「選定内のテストの結果で、この ID の全テスト・全寸法を確かめたことは示しません」を付ける。ID の全テストの数は、tests/e2e 全体を収集しないと分からないため（段階2で全体の収集を加えて「N/M」を出すかは、段階2の設計で判断する。第11章）。

#### 5.1.4 選定実行の境界条件と判定

| 事象 | 選定実行での扱い（設計案） | 備考（既存の動作） |
|---|---|---|
| 選定範囲が全件 call で成功、ほかの段階の失敗なし | 「選定範囲：成功」、終了コード 0 | — |
| call の失敗 | 失敗 | 既存の `on_report()` で記録 |
| setup・teardown のエラー | 失敗（段階と時刻を理由に記録。1 テスト1件） | 既存。call 成功後の teardown のエラーも失敗に上書きされる |
| スキップ（ブラウザを起動できない、Playwright がないを含む） | 失敗。報告を失敗に書き換え「[選定実行] スキップは失敗として扱います」 | 必須・準備確認と同じ扱いを選定実行にも適用 |
| xfail | 失敗（期待した失敗は選定範囲の成功ではない） | 現在の E2E に xfail はない（`tests/` を検索して0件）。既存の必須受入検証では skip 扱いから失敗になる |
| XPASS（strict でない） | 失敗（要確認として理由を記録） | 既存の必須受入検証では成功として数える。**必須受入検証の扱いは変えない**（第10章の残余リスク） |
| 0 件（`-k` の誤りなどで E2E が選ばれない） | 失敗（「0 件」） | pytest の終了コード 5 はそのまま保つ |
| 収集エラー | 失敗（「収集エラー」）。E2E が0件でも記録を書く | `on_session_finish()` の早期の return を選定実行では行わない。pytest の終了コード（2 を想定。実装で確認）を保つ |
| 途中の中断（Ctrl+C、`-x`） | 失敗（選定範囲内の未実施 N 件） | 終了コード 2 などを保つ |
| `-k`・`-m` で選定範囲から外れたもの | 範囲外（失敗にしない） | 選定実行では「未実施」と呼ばない |
| 照合の不一致（第5.3節） | 失敗（「照合の不一致：期待にない N 件・期待にあって実行されない M 件」） | — |
| 記録（`e2e-report.md`）が書けない | pytest 側では例外として表れる（既存と同じ）。スクリプト側で「記録なし」を失敗にする（第5.4節） | — |

- **終了コードの責任（pytest 側）**：選定実行で判定が「選定範囲：成功」でなければ、終了コード 0 を 1 にする。0 でない値（2 中断・収集エラー、3 内部エラー、4 使用法の誤り、5 0 件）は保つ。これで「終了コード 0 なのに対象がすべてスキップ」を選定実行では起こさない。
- **終了コードの責任（スクリプト側。段階2）**：pytest の終了コードに加え、記録の有無・判定の値・照合の結果を確かめる（第5.4.4節）。
- 選定実行の記録の追加の行（設計案）：「選定範囲の結果」（成功・失敗・スキップ・未実施の nodeid 数）、「範囲外」（除外 K 件、範囲外の必須項目 X 項目）、「全必須 E2E（C）」（「未実施（この実行は選定実行）」）。既存の行のラベルは変えない。
- 「結果（テスト単位）」の行：必須・準備確認は既存の書式のまま。選定実行・通常の実行・対象外では「未実施」から除外を分け、「成功 N・失敗 0・スキップ 0・未実施 0（除外 K）」とする（方針 第5.6節の表の改訂を同じ PR で行う）。

### 5.2 通常の pytest で E2E を除外したときの表示（段階1：10.2 の2）

- 区分「E2E 対象外」では、端末の節を1行にする（設計案）：「実ブラウザテスト（E2E）：この実行では対象外です（-k・-m で N 件を除外）。判定はありません。通常の pytest の合否は、pytest の要約行と終了コードで判断してください。」
  - 「判定: 不合格」「成功」の語を出さない。pytest の要約行（failed・error）と終了コードは pytest が通常どおり出し、隠さない。
  - `--e2e-report` を付けた場合だけ、区分「E2E 対象外」・判定「判定なし（E2E は対象外）」の記録を書く。
- 必須受入検証が有効な実行（`-m "not e2e" --e2e-required` や `FTA_E2E_REQUIRED=1` が残っている場合）は対象外の表示にしない（第5.1.2節）。端末にも「必須受入検証は不合格です」を既存どおり出す。
- 区分「収集のみ」では、節を「収集のみ（実行していません）。収集した E2E N 件」の1行にし、判定を出さない。

### 5.3 選定の一覧と照合（段階1：10.2 の4 の pytest 側）

- `--e2e-selection-out PATH`（設計案／未実装）：収集の後（`pytest_collection_finish`）に、選定範囲の nodeid の一覧を書く。`--collect-only` と通常の実行のどちらでも書く。
- `--e2e-expected-selection PATH`（設計案／未実装）：選定実行で、`--e2e-selection-out` の形式のファイルを読み、**今回の選定範囲の nodeid の集合**と比べる。差があれば実行前に失敗にするか（収集の直後）、実行後の判定を「選定範囲：失敗（照合の不一致）」にする。どちらにするかは実装で決めるが、**どちらでも終了コードは 0 にしない**。
- 形式（設計案）：UTF-8（BOM なし）の JSON。

```json
{
  "format": "fta-e2e-selection/1",
  "sha": "<40桁。取得できなければ null>",
  "dirty": false,
  "args": ["pytest", "-m", "e2e", "..."],
  "collect_only": true,
  "viewport_set": "base",
  "browser_channel": "chrome",
  "e2e_selected": true,
  "deselected_count": 24,
  "items": ["tests/e2e/test_new_analysis_page.py::test_E_N01_...[1280x800]", "..."]
}
```

- 照合の条件（設計案）：`sha` が一致し、`items` の集合が一致すること。件数だけが同じで別のテストが実行された場合も、集合の差で検出する。`viewport_set`・`browser_channel` が違えば不一致として記録する（寸法の組が違うと nodeid が変わるため、多くの場合は `items` でも検出される）。
- 照合の結果は `e2e-report.md` に行「選定の照合」（「一致（N 件）」／「不一致：…」／「照合なし」）として出す。「照合なし」は選定範囲の成功を妨げないが、段階2のスクリプトでは照合を必須にする。
- 収集の記録は実行の成功ではない。`--collect-only` の実行は区分「収集のみ」で、判定を出さない（第5.1.1節）。

### 5.4 Windows の部分実行のモード（段階2：10.2 の3・4）

#### 5.4.1 指定のしかた（設計案／未実装）

```powershell
& $ps1 -Mode Partial -Channel chrome -Venv $venv -OutRoot $out -ExpectedSha $sha `
    -Targets "tests/e2e/test_new_analysis_page.py", "tests/e2e/test_pr7_viewports.py::test_E_V01_list_and_new_screens" `
    -Keyword "E_N01 or E_V01"
```

- `-Mode Partial`、`-Targets`（`[string[]]`、必須）、`-Keyword`（任意。pytest の `-k` に渡す）。名前は段階2で確定する。
- 引数の検証（実行前の確認。違反は終了コード 9 で中止し、記録フォルダもテストも作らない）：
  - `-Targets` がない・空 → 中止（**対象未指定で全件を実行しない**）。
  - 各対象は `fta_tool` からの相対の nodeid か、ファイルのパス。`\` は `/` に正規化する。`tests/e2e/` で始まり、`::` の前のファイルが `-Source` の中に実在すること。ディレクトリ（例 `tests/e2e`）は受け付けない（全件は Full で行う）。
  - `-Mode Partial` 以外で `-Targets`・`-Keyword` を指定したら中止（既存のモードの意味を変えない）。
  - `-Keyword` が空白だけ → 中止。
- 対象は `Join-Path $S.Source` で絶対パスにして pytest に渡す（既存の Full も `"$Source\tests"` を絶対パスで渡し、作業フォルダは記録フォルダ。`pytest.ini` により nodeid は `fta_tool` からの相対になる。既存）。

#### 5.4.2 既存の仕組みの再利用

| 既存（`Invoke-Run`） | 部分実行での扱い |
|---|---|
| venv の確認、`-OutRoot` がコードの外、SHA の取得、未コミットの変更なし、`-ExpectedSha`、コード側の `.env` なし、ブラウザの実行ファイル、記録フォルダの長さ | そのまま使う（同じ関数の中で `Partial` を分岐） |
| 記録フォルダ名 `<SHA7桁>-<日時>-<channel>-<mode>` | `-partial` で作る。既存の記録には書かない |
| 環境変数の保存・設定・解除・`finally` での復元 | そのまま使う。`FTA_E2E_REQUIRED` を解除し、`--e2e-required`・`--e2e-preflight` を付けない。成功・失敗・中断（Ctrl+C）・例外のどの経路でも呼出し元の値に戻ることを試験する |
| `Start-Process` の標準出力・標準エラーの分離、子孫のプロセスの記録と後始末 | 収集と実行の両方に使う |
| `--e2e-env` のラベル（利用者環境／開発環境、OS、ブラウザ、headed） | 「部分実行」を加える |
| 診断用の環境変数 | `FTA_E2E_ACCESS_LOG` が設定されていれば、その有無とパスを `run-info.md` に記録する（設計案。値の変更・解除はしない） |

#### 5.4.3 収集と実行の条件の一致

- 同じ関数で引数の配列を1回組み立て、収集には `--collect-only -q --e2e-selected --e2e-selection-out <記録フォルダ>\selection-collected.json` を、実行には `--e2e-selected --e2e-expected-selection <同じファイル> --e2e-report ...` を**追加するだけ**にする（対象・`-m e2e`・`-k`・`--browser chromium`・`--browser-channel`・寸法の組を共通にする）。
- 収集の前後で SHA と未コミットの変更を確かめ直す（収集と実行の間にコードが変わったら中止）。
- 収集の結果で中止する条件（終了コード 9、テストは実行しない）：収集の終了コードが 0 でない（5 の 0 件を含む）、`selection-collected.json` がない・読めない、0 件。

- 結果の扱い：実行は試験の記録ではなく調査の記録（A・B・C に数えない）。

### 7.4 T3：報告と扱い

| 結果 | 扱い |
|---|---|
| T1・T2 で再現しない | 「今回は再現しなかった（条件）。原因未確定・未解消のまま」と報告し、継続事項として次の Windows の C で再び記録するかを利用者が決める |
| 再現し、(a)〜(c) に分類できた | 分類と根拠を報告し、追加の調査（例：ブラウザの通信の記録 NetLog。PR #31 では追加しないと利用者が判断した）の要否を利用者が決める。修正が必要なら別の PR で、方針 第4節で範囲を選ぶ |
| 再現したが分類できない | 原因未確定として報告。取った証跡を保存し、追加の調査の案を示す |

- 解消の条件にしないもの：Full の無制限な再実行、待ち時間の延長やリトライの追加だけの変更。T2 の回数は事前に決め、結果を見て回数を足さない（足す場合は理由と元の結果を残す。方針 第7.1節）。

### 7.5 C で再発した場合

- 段階1〜3やほかの PR の必須の Windows の Full で PR4-LAYOUT が失敗した場合、その Full は**不合格**として記録する。独立の調査であることを理由に合格にしない。
- 扱いは方針 第7.2節（原因未確定は合格として扱わず、再現の試験と調査の方法を記録して利用者に報告）と第7.3節（必要な確認を省くなら例外判断）による。再試験の範囲は第7.2節の3により選び、Full を無条件に繰り返さない。

## 10. 残余リスク

- 選定実行は明示のオプションでだけ厳しく判定する。オプションを付けない部分実行では、スキップ・0 件で終了コード 0 になりうる（現在と同じ）。方針 第5.2節で、A・B の部分実行には `--e2e-selected`（段階1の後）を付けることを求める改訂で補う。
- 必須受入検証の XPASS（strict でない xfail の成功）は、既存どおり成功として数える。現在の E2E に xfail はなく、影響はない。扱いを変える場合は全必須 E2E の判定の変更として別に判断する。
- 選定実行の ID の欄は「選定内のテストの結果」にとどまり、ID の全テスト・全寸法の確認を示さない。人の記録で ID を「確認済み」と要約する誤りは、段階3の補助が ID 単位で成功と書かないことと、方針 第6章の欄で補う。
- PowerShell 5.1 の引数の受け渡し・文字コードは、開発環境（pwsh、Linux）では完全には再現できない。Windows の確認で補う。
- PR4-LAYOUT の停滞は未解消のまま。段階の Windows の Full で再発すれば、その Full は不合格となり、段階の受入が遅れる可能性がある（第7.5節）。
- 段階3の Windows の C は方針上必要だが、変更の性質に対して負担が大きい。省略には例外判断か方針の改訂が要る。
